# dev_base への提案 — `_drafts` を `_proposed` にする

> **宛先:** `dev_base`（7分類の docs レイアウトを定義している側）
> **出どころ:** Affiliate-Management-Platform（`dev_base` に従っているリポジトリの1つ）
> **日付:** 2026-09-20
> **状態:** 提案。まだ渡していない。**出どころのリポジトリでは実施済み**
> （`docs/_drafts/` → `docs/_proposed/`。2026-09-20）

この文書は**逸脱の記録ではない。** 逸脱として各リポジトリに書き残すと、同じ問題を
次のリポジトリがまた踏む。上流の定義そのものを直すための提案である。

**以下に出てくる `_drafts` は、提案の宛先である `dev_base` 側の名前か、
改名前に実測した証拠を指す。**出どころのリポジトリの現在のパスではない。
証拠を当時の名前のまま残すのは、**なぜ改名したのかを読めるようにするため**である。

## 1. 提案

**7分類レイアウトの `_drafts/` を `_proposed/` に改める。**

```
docs/  1-requirements 2-setup 3-development 4-operations
       5-project-management 6-testing 7-references _drafts
                                                   ↑ ここ
```

---

## 2. なぜ — 名前と中身が逆を向いている

**下書き（draft）は「まだ見せられないもの」。提案（proposal）は「見せるために作ったもの」。**

`_drafts` という名前は前者を宣言している。ところが実際にそこへ置かれるのは、
**人に見せて判断を仰ぐために作ったもの**である。設計案、画面のモック、検討中の構造。
どれも「見られること」が存在理由で、見られないなら作る意味がない。

名前が「まだ見せられない」と言い、中身が「見せるために作った」と言っている。
**この食い違いは、実際に運用を歪める。**

---

## 3. 実際に起きたこと（このリポジトリでの証拠）

抽象論ではなく、**2026-09-20 に実物で確認した**3つの事実を挙げる。

### 3.1 `_drafts/` の中身は、製品としてライセンシーに配布されていた

このリポジトリは private/public の2本構成（`release-repo-split`）で、
`scripts/make-release.ts` が配布ファイル集合を定義している。

```
const INCLUDE = [ "src", "test", "scripts", "prompts", "docs", ... ];
```

`docs` が丸ごと入っており、`EXCLUDE` に `docs/_drafts/` は**無い**。
つまり `_drafts/design/` の設計キャンバス24枚は、**ライセンシーのリポジトリに届いている。**

そして、それは事故ではなかった。`test/release.test.ts` が固定している:

```
・docs/_drafts/design/Main.dc.html は配布物に入ること
・docs/_drafts/ に置いた未コミットの走り書きは入らないこと
```

**「`_drafts` の中身は配る」という振る舞いが、テストで守られている。**
名前だけが取り残されていた。

### 3.2 「下書き置き場」だと思われていたので、品質の基準が適用されていなかった

配布物だと認識されていなかった結果、**製品に適用しているはずの規則が、ここだけ免れていた。**

このリポジトリには「ライセンシーは端末を持たない」という要件があり、
承認画面の文言から端末コマンドを取り除く作業を丸一日かけて行った。
ところが同じ日、`_drafts/design/onboarding/Connect.dc.html` の**画面コピー**にこう書いてあった:

> 途中でやめても、`amp setup --resume` で続きから再開できます。

**同じ要件違反が、別の扉から配布されていた。**「下書きだから」という理由で、
誰も検査対象に含めていなかった。

### 3.3 実装済みと未実装が無印で並び、**説明文のほうが間違っていた**

`_drafts/design/` の24枚には、**実際に動いている画面**と**まだ実装が無い提案**が
混在している。板そのものにも、そこから生成される一覧にも、その区別は書かれていなかった。

**当初この節は「README には書いてあった」と書いていた。**24枚をコードで判定したら、
**その README が間違っていた。**訂正として残す。

- README は3つの画面を「まだ実装が無い」「実装より先」と書いていたが、
  **9日前のリリースで実装されていた。**消し忘れである
- つまり**製品にある画面を「まだ無い」と説明したまま、ライセンシーに配っていた**
- さらに版の取り違えが2件（板が増えた日と、機能が入った版を混同していた）
- README の「状態」列は「板が対話するか」と「機能があるか」の**2軸を混ぜていて**、
  そのせいで誰も矛盾に気づけなかった

**これが「下書き置き場」の本当の代償である。** 配布物の説明文が9日間間違っていて、
誰も検査しなかった。**製品文書なら、まず気づかれていた。**

配布物だと分かっていれば「どれが動くのか」を書かずに出すはずがないし、
書いたものが腐っていれば直っていたはずである。
**「下書き」という名前が、その問いを立てさせなかった。**

---

## 4. `_proposed` にすると何が変わるか

名前を変えるだけで、次の3つが自動的に正しくなる。

| | `_drafts` のとき | `_proposed` にすると |
|---|---|---|
| 配布 | 「下書きを配っている」＝矛盾 | **提案を見せている**＝目的どおり |
| 品質 | 「下書きだから」で検査を免れる | **見せる物なので、見せる物の基準がかかる** |
| 中身 | 実装済みと提案が無印で混在 | **「提案」と名乗る棚なので、実装済みには印が要る**と分かる |

3番目が効く。**棚の名前が「提案」なら、そこに実装済みの物を置くときは印が要る**、
という問いが自然に立つ。`_drafts` では立たなかった。

## 5. さらに踏み込むなら（任意）

`_proposed` は依然として 1〜7 の番号の**外**にいる。番号は読む順番を表しているので、
外にあることは「読まなくてよい」と読める。

だが上の 3.1 が示すとおり、中身は**配布される製品文書**である。だとすれば、
**番号の中に入れる**ほうが筋が通る（たとえば `3-development/proposed/`）。

- **`_proposed` のまま外に置く** — 最小の変更。「確定していない」という位置づけは残る
- **番号の中に入れる** — より正直。ただし7分類の構造を触るので影響が大きい

**この提案の本体は名前のほうで、置き場所の移動は別の判断として分けたい。**
名前が直れば、置き場所の問いは後からでも立てられる。逆は立たない。

## 6. 移行について — 確かめるべきことが1つある

改名は、**下流のリポジトリでは「旧ディレクトリの削除 ＋ 新ディレクトリの追加」として届く。**

更新を同期する仕組みが**削除を伝えない実装**だった場合、相手の手元に
**旧 `_drafts/` が残り、新旧2つの同じ物が並ぶ。**
これは「1つの問いに2つの答え」であり、避けたい形である。

### このリポジトリでは確かめた。安全だった（2026-09-20）

**当初この節は「危険かもしれない」と書いていた。実測して、この repo については覆った。**
訂正として残す — 確かめずに危険と書くのも、確かめずに安全と書くのと同じくらい悪い。

2つのホップ（上流 → 公開リポジトリ → ライセンシー）が**両方とも `rsync --delete`**:

- `.github/workflows/sync-to-release.yml` — `rsync -a --delete`。コメントが理由を書いている:
  *「--delete so a file removed upstream is removed downstream too; an orphaned module
  left behind in a licensee's fork is worse than a gap.」*
- `release-assets/take-updates.yml` — `rsync -a --checksum --delete`、`--exclude` は
  `.git` ・ `.github` ・ `platform.config.yaml` ・ `wrangler.jsonc` の4つ

改名した状態で実際に1回同期すると、`D docs/_drafts/…` と `A docs/_proposed/…` が
同じコミットに乗り、**旧ディレクトリは空のまま残ることもなく消えた。**
除外したパスは `--delete` からも保護されるので（`--delete-excluded` を付けていない）、
**除外と削除は両立している。**

**それでも各リポジトリは自分で確かめること。** ここで安全だったのは
`--delete` が書いてあったからで、書いていない経路なら結論は逆になる。

### ⚠️ ついでに見つかった、改名とは別の穴

同じ実測で、**ライセンシーが自分で足したファイル（`MY-NOTES.md`）が消えた。**
除外リストに無いものは削除される。`take-updates.yml` は「deliberately leaves alone」として
4つを挙げるだけで、**それ以外が消えるとはどこにも書いていない。**

PR に `D` として出るので気づけるが、PR 本文もこれに触れていない。
**`dev_base` が同種の同期を定義しているなら、そちら側にも同じ穴がある可能性が高い。**

## 7. まとめ

- **名前と中身が逆を向いている。** 下書きは見せない物、提案は見せる物
- **実際に配布されていて、テストでそう固定されている。**名前だけが古い
- **「下書きだから」が、製品の基準を免れる口実になっていた**（要件違反が1件、実際に配布された）
- **説明文そのものが9日間間違っていて、誰も気づかなかった**（実装済みの画面を「まだ無い」と
  書いたまま配っていた）
- **提案という名前は、実装済みに印を付ける必要を自分から気づかせる**
- 移行時は、**更新経路が削除を伝えるかを先に確かめること**
