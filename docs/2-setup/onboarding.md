# オンボード設計 — ライセンシーの最初の1時間

> **これは設計であって、まだ実装ではない。** `amp setup` / `amp venture add` /
> `.amp/setup.json` はこの文書の中にしか存在しない。既定の置き場所を
> Cloudflare にするなら、下の「Cloudflare を既定にしたときの最初の1時間」が
> 本線で、9ステップはその中身になる。何がすでにあって何が新規かは
> 「実装として何が要るか」の表にある。いま使えるのは `amp init` と設定ファイルの直接編集。

いまの最初の1時間はこうなっている。

```
git clone → npm install → amp init → 428行のYAMLを開く → …
```

**428行のYAMLを開いた瞬間が、いちばん脱落する場所。** しかもそこで求められるのは、
Threadsの長期トークン（Meta開発者コンソールを何画面か通る）と、ASPの案件情報と、
公開ドメインの用意。**どれも、まだこのソフトが自分の役に立つと分かる前に要求される。**

順番が逆になっている。

---

## 設計の原則

**1. 資格情報を1つも持たずに、製品が動くところまで行けること**

APIキーもSNSトークンもASP口座も無い状態で、企画10案 → 承認 → 執筆 → 検品 → 枠決め →
投稿（シミュレーション）まで通す。**「これは自分の役に立つ」と分かってから、
Metaの開発者コンソールを開いてもらう。**

いま逆になっているのは、`doctor` が最初に来て、鍵が無いと止まるから。

**2. 高い作業ほど後ろに置く**

| 作業 | 所要 | 失敗しやすさ | 今の位置 | あるべき位置 |
|---|---|---|---|---|
| ニッチ・読者・文体を決める | 10分 | 低 | 2番目 | 2番目 |
| 1日を通して見る | 2分 | なし | できない | **3番目** |
| Anthropic キー | 3分 | 低 | 1番目 | 5番目 |
| Threads トークン | 20〜40分 | **高** | 1番目 | 6番目 |
| ASP案件の登録 | 15分 | 中 | 1番目 | 7番目 |
| 公開ドメイン | 30分〜 | **高** | 1番目 | 8番目 |

**3. 設定ファイルは生成するもので、UIが編集し続けるものではない**

承認画面が `platform.config.yaml` を書き換える設計にはしない。理由は2つ。

- **コメントが設定の説明そのもの。** 428行のうち大半はコメントで、なぜその値なのかを
  説明している。オブジェクトをシリアライズして書き戻すとそれが消える。
- **「自分の設定は何か」の答えが2つになる。** フォークして中を読む人にとって、
  真実が1箇所であることが監査の前提。

代わりに、**セットアップはテンプレートを埋める**。コメントはテンプレート側にあるので残る。
一度生成したあとは、本人がエディタで編集する。運用アカウントを増やすときも `amp venture add` が
コメント付きのブロックを追記する。**生成器であって、常駐エディタではない。**

## どこに何を入れるか

| 置き場所 | 入るもの | 誰が触るか | なぜそこか |
|---|---|---|---|
| **セットアップ（1回きり）** | 会社名・アカウント定義・文体・資格情報・案件・ドメイン | 初回のみ | 最初の1本までを塞いでいるもの全部 |
| **`.env.local`** | 鍵とトークンのみ | 本人、手で | YAMLにもUIにも秘密は置かない |
| **`platform.config.yaml`** | それ以外すべて | 本人、エディタで | 差分が読めて、更新で壊れない |
| **`prompts/`** | 各役割の考え方 | 本人、文章として | 文章を変える手段は文章 |
| **承認画面（毎日）** | 1日2回の判断と、停止 | 運用者 | **設定は置かない** |

**承認画面に設定を置かない**のは制限ではなく分担。あの画面の仕事は
「30秒で2つ決める」であって、増やすと両方が悪くなる。

## 9ステップ

前半5つは**アカウントも鍵も要らない**。

### 1. 名乗る（30秒）
会社名と自分の名前。承認画面のヘッダと明細に出る。

### 2. アカウントを定義する（10分）
ニッチ、読者、市場（＝どの国の広告規制に従うか）、タイムゾーン、言語。
**このソフトが推測できない唯一の情報。**

市場を選ぶと、開示文・禁止表現・規制当局が自動で決まる。ここは書かせない。

### 3. 文体を決める → その場で3行出す（5分）
一人称、トーン、使いたい言い回し、絶対に使わない言い回し。

**入力し終わった瞬間に、その文体で書かれたフックを3つ出す。** モックで動くので費用ゼロ。
ここが「動いた」と分かる最初の瞬間で、**セットアップ全体でいちばん重要な30秒**。
気に入らなければその場で直す。文体の調整は、投稿を見ないと絶対に決まらない。

### 4. 良いと思う投稿を5つ貼る（10分）← 新規、いちばん効く

**コールドスタート対策。** いまの設計だと初日は、パターンゼロ・実績ゼロ・数字ゼロで
分析担当が走る。**初日の提案品質は、その後で最も悪い。** そして初日こそ、
運用者が「使えるか」を判断する日。

自分の過去投稿でも、他人の良い投稿でもいい。5つ貼ると、リサーチ担当がそこから
**再現可能な型**を抽出して、プレイブックの初期値にする。証拠は「初期投入」として記録され、
自分の実績が溜まると自然に置き換わる。

初日が「何も知らない状態」から「5つの仮説を持った状態」に変わる。

### 5. 1日を通す(2分)
モックで丸ごと1サイクル。10案 → 承認 → 執筆 → 検品 → 枠 → 投稿（出ない）。
**ここまで、鍵は1つも要らない。**

ここで気に入らなければ、Metaの開発者コンソールを開かずにやめられる。それでいい。

### 6. モデルの鍵（3分）
`ANTHROPIC_API_KEY`。ここで初めて課金が発生するので、**何にいくらかかるかを先に見せる**
（1サイクルあたりのおおよそのトークン数は、5で実測済み）。

### 7. チャネルをつなぐ（20〜40分）← いちばん難しい
Threadsの長期トークン。Meta開発者コンソールの手順を画面内に置き、
**貼った瞬間に検証**して、失敗理由を名指しで返す（権限不足なのか、期限切れなのか、
プロアカウントでないのか）。

ここで詰まる人が最も多い。**セットアップを中断して後で再開できること**が要件。

### 8. 案件を登録する（15分）
ASP、ランディングURL、単価、通貨、市場。

**越境の注意書きが必須になる理由を、その場で説明する。** 「US案件を日本の読者に出す」を
選んだ瞬間に、決済通貨・サポート言語・販売元の3点を求める。あとで
「なぜ必須なんだ」と思われないように、選んだ直後に理由を出す。

### 9. リンクのドメインと、計測の確認（30分〜）
`tracking.baseUrl` と、その前段。

**ここで必ず言う:** そのドメインは承認画面にも届く。`/go/` だけではない。
だから `AMP_CONSOLE_TOKEN` を設定してから公開する。
（この露出は実際にセキュリティレビューで見つかったもの。5節の警告として実装済み。）

最後に計測経路を確認して、`measurement: closed` になったら1本目。

## Cloudflare を既定にしたときの最初の1時間

**メールで送るのはボタン1つ。** リポジトリへの招待でも `git clone` でもない。

```
メールのボタン ──► Cloudflare のサインアップ（無料。カード不要）
                    │
                    ├─ リポジトリがライセンシーの GitHub に複製される（フォークは残る）
                    ├─ D1 と Durable Object が自動で作られて紐づく
                    ├─ 鍵を貼る画面が出る（ANTHROPIC_API_KEY と承認画面のトークン。
                    │   それぞれ「どこで取るか」の説明つき）
                    └─ ビルドしてデプロイ。以後、push するたび自動で再デプロイ
                    │
                    ▼
  https://amp-<名前>.<自分のサブドメイン>.workers.dev/?token=… が開く
                    │
                    ▼
        承認画面の中のセットアップ（ニッチ・読者・市場・文体 → その場で3行）
                    │
                    ▼
        できた設定を「コピー」→ 自分のリポジトリに貼って保存 → 自動で再デプロイ
```

Cloudflare の **Deploy to Cloudflare ボタン**がこれを担う。リポジトリを
ライセンシーのアカウントに複製し、`wrangler.jsonc` に書いた D1 や Durable Object
を自動で作って紐づけ、`.env.example` に並べた秘密を「説明つきの入力欄」として
出し、ビルドして配置し、CI/CD まで繋ぐ。**こちらが用意するのは README のボタン1行と、
その3つのファイルだけ。**

### ドメインは要らない

`<worker名>.<サブドメイン>.workers.dev` が無料で付き、**公開される。**
`/go/<code>` はそこで動くので、**計測経路は初日から閉じる。** これが
「ドメインの用意に30分〜」という最大の関門を丸ごと消す。

ただし Cloudflare 自身は `workers.dev` を「趣味・個人向けで、事業の中核には
勧めない」と書いている。**始めるには十分、育ったら独自ドメインに移す**という
案内にする（ダッシュボードの Domains タブから、購入も接続もその場でできる）。

### 承認画面が設定を書けない、という制約の裏返し

Workers のファイルシステムは読み取り専用なので、セットアップ画面は
`platform.config.yaml` を保存できない。**だから「できあがった YAML を表示して、
コピーして、自分のリポジトリに貼る」**という形にする。貼って保存すれば push になり、
自動で再デプロイされる。

これは妥協ではなく、元の思想（設定はライセンシーのもの、履歴は git に残る）
そのままである。1回の貼り付けで済み、その1回が「自分の設定を自分が持っている」
という理解を最初に作る。

### 設定が無い状態で起動できること

上の流れは、**設定がまだ無い状態で Worker が立ち上がってセットアップ画面を出せる**
ことが前提になる。いまの `createRuntime` は設定が読めなければ失敗する。
Workers 版の入口は、設定が無いときだけセットアップ画面を返す。

## 端末から入れたい人のために（Docker / 自前サーバの経路）

ブラウザで見せたいが、**承認画面に載せてはいけない**。認証を設定する前に
認証つきの画面は開けないので、鶏と卵になる。

`gh auth login` や `stripe login` と同じ形にする。

```bash
amp setup
```

- `127.0.0.1` にだけ束ねた一時サーバを立てる
- 一度きりのコードを含むURLを端末に出す
- 完了したら自分で終了する
- 書くのは `.env.local` と `platform.config.yaml` の2つだけ
- **中断して `amp setup --resume` で再開できる**（7で詰まるため）

端末だけで済ませたい人のために、全ステップは `amp setup --cli` でも通せる。

## 実装として何が要るか

| # | もの | 状態 |
|---|---|---|
| 0 | Deploy to Cloudflare ボタン（README 1行 ＋ `wrangler.jsonc` ＋ `.env.example` ＋ `package.json` の説明文） | 新規。Cloudflare 経路ではこれが1〜2の代わりになる |
| 1 | 設定テンプレートの穴埋め生成器 | 新規。`platform.config.example.yaml` をテンプレート化。**Cloudflare 経路では「YAML を表示してコピーさせる」まで** |
| 2 | `amp setup`（一時サーバ ＋ 画面） | 新規。Docker / 自前サーバ経路だけで必要 |
| 2b | 設定が無くても起動してセットアップ画面を出す Worker | 新規。Cloudflare 経路の前提 |
| 3 | 文体のプレビュー（モックで3行） | **既存で足りる**（`llm/demo.ts`） |
| 4 | 参考投稿投入 → 初期パターン抽出 | 新規。リサーチ担当の既存経路を使う |
| 5 | 資格情報の即時検証 | **ほぼ既存**（各アダプタの `healthCheck`） |
| 6 | 計測経路 | **実装済み**（`domain/measurement.ts`） |
| 7 | `amp venture add` | **半分ある。** 探索担当の採用が、コメント付きブロックを `ventures:` に追記する生成器そのもの（`src/kernel/exploration.ts` の `appendVentureBlock`）。人が書いた定義から同じ追記をする入口だけが無い |
| 8 | 中断と再開 | 新規。`.amp/setup.json` に進捗 |
| 9 | 「初期投入由来」の記録 | 新規。証拠の `source` は今 `swipe` / `own_post` の2値で、参考投稿から入った型を後から数えられない |

**3・5・6はすでにある。** 新規に要るのは、生成器と、それを見せる画面と、
参考投稿からの初期化と、その由来の記録。

## 測り方

オンボードの成否は感想では分からない。`amp setup` は各ステップの
開始・完了・離脱を `.amp/setup.json` に記録する（送信はしない）。先行利用者には
そのファイルを送ってもらう。

見るのは1つ。**ステップ5（1日を通す）に到達した人のうち、何人がステップ9まで行くか。**
5に着いた人は製品を理解している。そこから落ちるなら、原因は製品ではなく手順にある。
