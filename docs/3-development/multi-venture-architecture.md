# 複数の運用アカウントをどう運ぶか — アーキテクチャ提案

> **提案であって、実装ではない。** 実装済みなのは0節に書いた現状と、4節(a)の
> `doctor` による計測経路の検査だけ。`StoreRegistry`、`.amp/ventures/`、ロール、
> `experiments:`、`amp venture forecast` / `dossier` はどれもまだ無い。特に
> `experiments:` を `platform.config.yaml` に書いても、未知のキーは黙って無視される。

対象読者は4人いる。この文書は、4人の利害が衝突する場所を先に見つけて、
**どれを守り、どれを諦めるか**を決めるためのもの。

| | 誰 | いちばん困ること |
|---|---|---|
| A | プラットフォーム開発者（ライセンサー） | コンプラのバグを直したのに、6つのフォークのうち2つにしか届かない |
| B | ライセンシー（20アカウントの運用者） | アカウントを1つ増やすのにサーバ作業が要る。全体でいくら儲かっているか分からない |
| C | プロジェクト運用責任者（1アカウント担当） | 自分のアカウントだけ見たいのに全部見える。逆に、他人が自分のアカウントを壊せる |
| D | 育ったアカウントの買い手 | 「このプレイブックは本当にこのアカウントが学んだものか」を確認できない |

**この4人のうち、アーキテクチャを決めるのは D。** 他の3人の要求は後から足せるが、
Dの要求（1アカウントを、他から切り離して、証明可能な形で丸ごと渡せること）だけは
データの置き方そのものなので、後から足せない。

---

## 0. 今どうなっているか

- `platform.config.yaml` の `ventures[]` で**複数アカウントはすでに動く**。デーモンは
  ventureごとに時刻を見てサイクルを回す（`src/scheduler/daemon.ts`）。
- ドメインの型はすべて `ventureId` を持つ（`src/core/types.ts`）。**論理的には分かれている。**
- ただし `Store` はインスタンスに1つ。JSONアダプタは `.amp/` 配下に
  `cycles.json` `patterns.json` … と**全アカウントを混ぜて**置いている。
- 承認画面の認証は**単一のベアラートークン**。「誰が見ているか」の概念がない。
- LLMコストは `provider.stats()` でインスタンス全体。**アカウント別の原価が出ない。**

つまり「複数アカウントは動くが、1アカウントを切り離せない」状態。ここが今回の主題。

---

## 1. 3つの選択肢と、4人の採点

### 選択肢1: フォーク・パー・プロジェクト（アカウントごとにリポジトリ）

美容ケア用リポジトリ、育児用リポジトリ、教育用リポジトリ。それぞれ独立に動かす。

| | 評価 |
|---|---|
| A 開発者 | ✗ 直したバグが届かない。ライセンシーは開発者ではないので、6回のマージはしない |
| B ライセンシー | ✗ アカウントを増やすたびにデプロイ。全体像を見るには6箇所を人力で集計 |
| C 責任者 | ◎ 完全に自分の世界。他人が壊せない |
| D 買い手 | ◎ リポジトリごと渡せば終わり。混ざりようがない |

### 選択肢2: 共有データベースのマルチテナント（`venture_id` 列で分ける）

1つのサービス、1つのDB、全アカウントが同じテーブルに同居。

| | 評価 |
|---|---|
| A 開発者 | ◎ 1コードベース、1テストスイート |
| B ライセンシー | ◎ アカウント追加は行の挿入。全体集計はSQL1本 |
| C 責任者 | △ 分離はアプリ層の約束。`WHERE` の書き忘れ1つで隣のアカウントが見える |
| D 買い手 | ✗ **売却がエクスポートスクリプトへの信頼になる。** 「混ざっていない」を証明できない |

Dの✗は、法務や個人情報の話ではなく**商品性**の話。この製品の約束は
「このアカウントは自分で学んだ」であって、隣のアカウントの学習が漏れ込んだ瞬間、
売り物としての値段が説明できなくなる。

### 選択肢3（推奨）: 1コードベース・1プロセス・**ストアはアカウントごとに物理分割**

```
.amp/
  ventures/
    beauty-care/     ← 完結した1社
      cycles.json patterns.json drafts.json posts.json
      links.json clicks.json conversions.json audit.jsonl
    parenting/
    education/
  insights/          ← 派生データのみ（3節）。ここに「学習」の正本は置かない
```

| | 評価 |
|---|---|
| A 開発者 | ◎ 1コードベース。`Store` ポートは既存のまま、開き方が変わるだけ |
| B ライセンシー | ◎ アカウント追加はディレクトリ1つ。全アカウント一覧は各ストアを走査して集計 |
| C 責任者 | ○ 物理的に別。アプリ層の`WHERE`ではなく、**開いていないストアは読めない** |
| D 買い手 | ◎ `tar` 1つ＋ハッシュ。混ざりようがないことがファイルシステムで分かる |

**選択肢1の分離を、選択肢2の運用コストで手に入れる形**。これを採る。

### なぜこれが安く済むか

`src/storage/store.ts` のポートがすでに十分に狭い。変えるのは1箇所：

```ts
// Runtime は Store を1つ持つのをやめ、アカウントごとに開くレジストリを持つ
export type StoreRegistry = {
  for(ventureId: VentureId): Promise<Store>;  // 遅延オープン＋キャッシュ
  closeAll(): Promise<void>;
};
```

JSONアダプタは `dataDir` が1階層深くなるだけ。Postgresアダプタを書く日が来ても、
**ポートがアカウント横断の読み取りを許さない**ので、スキーマ分割でも `venture_id` 列でも、
この性質は生き残る。

### 例外: 何を共有に残すか

アカウントをまたいで**書き込む**ものは1つも作らない。共有に置くのは、アカウントが存在しなくても
意味があるものだけ。

- `platform.config.yaml` — 定義（アカウントごとに切り出して売却時に渡す）
- `prompts/` — ライセンサーが配る技芸。学習ではない
- ポリシー、AIっぽさヒューリスティック、チャネル整形 — コード
- `.amp/insights/` — **派生**。いつ捨てても再計算できるもの（3節）

## 2. 管理アプリは別に作るべきか

**別アプリにはしない。同じバイナリの別サーフェスにする。** ただし前提が2つ足りない。

理由:

- 別アプリにすると認証系が2つ、デプロイが2つ、その間のネットワーク境界の防御が
  ライセンシーの仕事になる。「フォークして動かすだけ」という売り文句が壊れる。
- 全アカウント一覧がやることは**読みが主・書きはライフサイクルだけ**（アカウントの作成／停止／
  売却）。承認画面と同じプロセスで足りる。

```
src/console/
  ui.ts        ← 既存。1アカウント・1日2回の判断（C が見る画面）
  portfolio.ts ← 新設。全アカウントの状態・通貨別の金額・滞留している承認（B が見る画面）
```

**別アプリが正解になる日は来る。** ライセンシーがアカウントを複数マシンに分散したときで、
そのときは同じ集計を「走査」ではなく「各インスタンスからの push」で作る。
集計の形が同じなら、その移行は差し替えで済む。今作る理由はない。

### 先に要る前提（これが今いちばん retrofit が高い）

1. **承認画面に「誰が見ているか」を入れる。** 今は単一トークン。
   `owner`（全アカウント）/ `manager`（割り当てられたアカウントのみ）/ `viewer`（読むだけ）の3ロールと、
   アカウントへの割り当て。Cの「他人が自分のアカウントを壊せる」を閉じるのはここ。
2. **アカウント別のLLM原価。** 今は `stats()` がインスタンス全体。レベニューシェアの明細を
   出す以上、原価もアカウント別でないと「このアカウントは黒字か」が言えない。
   `LlmProvider` に呼び出し元の venture を渡し、ストアに日次で積む。

## 3. アカウントをまたいだ学習をどう扱うか（ここが唯一、慎重にやる場所）

20アカウントを1つのインスタンスで回す**唯一の技術的な理由**が、これ。
「20アカウントを横断して見ると、日本の育児系では数字で始まるフックが弱い」——
これは1アカウントでは絶対に得られない知見で、フォーク運用に対する本当の優位性。

同時に、**Dの要求を壊しうる唯一の機能**でもある。だから設計を先に固定する。

- **正本は各アカウントのプレイブック。** `insights/` は派生であり、いつ消しても再計算できる。
- **集計のみ。** 個別の投稿・下書き・パターンの実体は入らない。「Nアカウント・M本の観測」まで。
- **アカウントごとにオプトイン。** 参加していないアカウントは集計にも入らないし、恩恵も受けない。
- **書き戻さない。** 既存アカウントのプレイブックを事後に書き換えることは絶対にしない。
  効くのは**新しいアカウントの初期パターンの種**としてだけ、しかも低い信頼度で。
- **由来を記録する。** 種から入ったパターンは監査ログに「事前分布 由来」と残る。
  これで買い手は「このパターンはこのアカウント自身の実績か、初期投入か」を数えられる。

この5つを守る限り、売却時に「初期投入由来の型は3件、うち0件が生存」と言える。
守らないと、この機能は製品の価値そのものを溶かす。

## 4. 事前計測 — 「始める前に分かること」を正しく定義する

新しいアカウントのコンバージョン率は予測できない。**予測できないことを予測すると製品が嘘をつく。**
代わりに、始める前に本当にできることが4つある。価値の高い順に置く。

### (a) 計測の完全性を、開始条件にする ← 最重要、実装も最も安い

「事前に計測できる仕組み」の実体はこれ。**1本目を投稿する時点で、計測経路が閉じていること。**

```
投稿 → トラッキングリンク → クリック → コンバージョン → 承認済み報酬 → パターンへ反映
```

5つとも実装済みだが、今は**計測経路が切れたまま運用アカウントを開始できてしまう**。
コンバージョンを返さないネットワークアダプタ、設定されていない `tracking.baseUrl`、
数字を返さないチャネル——1か月気づかない。

- `doctor` はアカウントごとに計測経路を検査し、閉じていなければ `measurement: INCOMPLETE` と
  直し方を出す（**実装済み**。ただし起動を止めはしない）
- そのアカウントの日報は、直るまで毎日いちばん上でそれを言う（未実装。日報そのものがまだ無い）
- 未計測期間は「実績なし」ではなく**「計測不能」として記録**する（未実装）。買い手にとって、
  この2つは全く違う

どんな予測モデルよりこれが先。

### (b) 期待値計算（決定論、モデルなし）

運用アカウントを作る画面で出す算数。予測ではなく、前提の明示。

```
到達 × 保存率 × クリック率 × 承認率 × 単価 = 月次期待報酬
必要投稿数 × 1投稿あたりのLLM原価 + チャネル固定費 = 月次原価
損益分岐に必要なクリック数 = ...
```

- 各入力の既定値は、**そのライセンシー自身の既存アカウント**から引く（3節の正当な用途）
- 既存アカウントがなければ「既定値なし」と表示する。業界平均をでっち上げない
- 出力は単一の数字ではなく幅。**どの入力を推測したかを併記する**
- `amp venture forecast <id>`

### (c) 実験を平時に埋め込む

探索枠はすでにある。これを**停止規則つきの宣言された実験**に格上げする。

```yaml
experiments:
  - pattern: pat_011
    hypothesis: "問いで始めるフックは、育児系では保存率を上げる"
    minPosts: 20
    minDays: 14
    retireBelow: 1.2   # 中央値比
```

分析担当は所感ではなく停止規則に対して報告する。これは運用の質の話であると同時に、
**アカウントの履歴を買い手が読める形にする**ための仕掛け。

### (d) 買い手が見る指標を、初日から持つ

アカウントは日次の数字では買われない。買われるかどうかを決めるのは90日の集計で、
**初日から記録していないと売却時に作れない**ものばかり。

- 収益の安定性（週次のばらつき）
- 収益の集中度（1つの案件に何%依存しているか）
- パターンの再現性（生存したパターン数 / 試した数）
- 規制リスクの履歴（指摘が何件出て、何件が公開前に止まったか）
- 初期投入由来の比率（3節の事前分布由来のパターンが、今どれだけ生き残っているか）
- 計測不能期間の割合（(a)）

これを1枚にしたものを **アカウント概況書（dossier）** と呼ぶ。
`amp venture dossier <id>` で生成し、A/B/C/D の4人全員が同じものを読む。
これが、1節でアカウントごとにストアを分けた判断の**答え合わせ**になる。

## 5. 開発順序

「後から直すのが高いもの」の順。上3つは利用者から見て何も変わらないが、
順番を間違えると全部やり直しになる。

| # | やること | 依存 | 目安 | 後回しにしたときの代償 |
|---|---|---|---|---|
| 1 | `StoreRegistry` とアカウントごとのデータ配置 | — | 中 | **最大。** 全データの移行 |
| 2 | 承認画面の識別とロール（owner/manager/viewer） | — | 中 | 大。承認の記録に誰がやったかが残らない |
| 3 | アカウント別のLLM原価 | 1 | 小 | 中。過去の原価は再構成できない |
| 4 | 計測の完全性チェック（`doctor` ＋ 日報） | — | 小 | 中。未計測期間が「実績なし」として残る |
| 5 | アカウントのライフサイクル（create / pause / archive / export / import） | 1 | 中 | 小。**create と archive 相当は実装済み**（探索担当の採用が設定に追記、`amp venture deactivate` が非アクティブ化）。export / import はストア分離（1）待ち |
| 6 | 全アカウント一覧 | 1,2 | 中 | 小。**実装済み**（`amp portfolio`・承認画面）。ただしストアは共有のまま、ロールもまだ無い |
| 7 | 期待値計算と実験の宣言 | 4 | 中 | 小 |
| 8 | アカウント概況書 | 4,5 | 小 | 小 |
| 9 | ライセンシー横断の事前分布（オプトイン） | 1,5,8 | 大 | なし（最後でよい。最後にすべき） |

9を最後にするのは、**間違えると製品を悪くする唯一の項目**だから。
1〜8はどれも「まだ無い」だけで済むが、9は「あるが信用できない」を作れてしまう。

## 6. 決めてもらう必要があること

1. **1インスタンスあたりの想定アカウント数。** 10ならJSONストアのままでよい。
   100を超えるならPostgresアダプタが5番より前に来る。ここで見積もりが変わる。
2. **プロジェクト運用責任者（C）の見え方。**
   (a) ライセンシーと同じ画面で、自分のアカウントだけ見える／
   (b) 自分のアカウントしか存在しないことになっている。
   (b) のほうが売却時にきれいで、Cの体験もよい。実装は (a) のほうが楽。
3. **「売却」の中身。** データ（プレイブック・履歴・案件との契約）を渡すのか、
   **稼働中のSNSアカウントごと**渡すのか。

   後者は要注意で、**Threads / Instagram を含む多くのSNSは、アカウントの
   譲渡・売買を利用規約で制限している。** 規約側のリスクを買い手に負わせない設計にするなら、
   売るのは「アカウント」ではなく「運用会社（データ＋プレイブック＋案件との契約＋概況書）」だと
   最初から定義しておくほうが安全。ここは法務判断が要る領域で、
   プラットフォーム側で断定はできない。**契約書のひな型に反映する前に確認が必要。**

## 7. この文書が変えないこと

- 人間の仕事は2つのまま。アカウントが20になっても、**1アカウントあたり1日2回**であって、
  ライセンシーが40回判断するのではない。全アカウント一覧は判断の画面ではなく、
  **どこが止まっているかを見る画面**。
- 役割は次に何が走るかを決めない。アカウントが増えても、決めるのはオーケストレータ。
- ガードレールはコードのまま。アカウントごとに緩められる設定にはしない。
