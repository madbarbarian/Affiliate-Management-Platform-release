# ストアをアカウントごとに分ける — 設計

> 2026-09-10 着手。[複数アカウントの提案](multi-venture-architecture.md) の retrofit 順の **1番**。
> 「後から直すのが高いもの」の筆頭で、移行コストはデータ量に比例する。
> [人を増やす](adding-people.md) の「ロールはこの後」も、これが土台。

## 1. なぜ今か

理由は2つあり、どちらも急ぐ理由が違う。

- **アカウントを売るとき。** この製品の約束は「このアカウントは自分で学んだ」。
  隣のアカウントの学習が混ざっていないことを、**エクスポートのコードを信じてもらう**以外の
  方法で示せない状態にある。
- **ロールを入れるとき。** 「この人にはこのアカウントしか見せない」を、画面の `if` ではなく
  ポートの外側で保証したい。画面の絞り込みは書き忘れられるが、渡していないストアは読めない。

**そして今日が一番安い。** サイクル3件・投稿3件。1年運用したあとの移行は365倍の行を動かす。

## 2. 採らなかった案

**D1をアカウントごとに1つ**（提案書のファイル時代の絵をSQLに直訳したもの）。分離は最強だが、
**Deployボタンの体験が壊れる**。アカウントを増やすたびにライセンシーが新しいD1を作って
`wrangler.jsonc` にバインディングを足すことになり、「設定ファイル1本、`src/` は触らない」という
この製品の約束と正面から衝突する。

**採るのは: 1つのデータベースのまま、`venture` 列で分ける。ただし絞り込みはポートの内側1箇所に閉じる。**
ファイルアダプタ側はディレクトリで物理分割するので、手元運用なら「開いていないものは読めない」が
そのまま成り立つ。

## 3. 形

```
StoreRegistry
  ├ for(ventureId)  → その1アカウントの Store。**他のアカウントは見えない**
  ├ each()          → 全アカウントぶん。**比べる仕事だけがこれを呼ぶ**
  └ close()
```

**`Services.store` は「1アカウントのストア」になる。** 役割もオーケストレータも、自分が今
どのアカウントの仕事をしているかを知っているので、渡されたストアがそのアカウントのものである
ことを前提にしてよい。`ventureId` で絞る `find` は不要になる（書き忘れも起きない）。

## 4. アカウントをまたぐ読み手は5つだけ。全部名前がある

またぐこと自体は正しい。**暗黙にできることが問題**なので、数えられる形にして、それ以外を
不可能にする。

実装して、**5つではなく8つ**だった。書いた時点で見落としていた3つは、どれも「画面から
来るのはidだけで、アカウントが付いていない」という同じ形をしている。

| # | 誰 | なぜまたぐのが正しいか |
|---|---|---|
| 1 | `buildPortfolio` | 比べるのが仕事。全アカウント一覧そのもの |
| 2 | 探索担当（スカウト） | 全アカウントの実績を読んで次の1つを提案する。提案と自身の履歴は `COMPANY_SCOPE` のストアに入る |
| 3 | `dispatchDue` | 枠の来た投稿を出す。どのアカウントのものかは問わない |
| 4 | 承認画面の「今日」 | 判断待ち・予約中・直近の数字・最近の動き。オーナーの1枚 |
| 5 | `/go/<code>` のリダイレクト | **読者はアカウントを知らない。**コードしか持っていない |
| 6 | `resolveGate` | 承認はidだけで届く。どのアカウントの決定かは、探して初めて分かる |
| 7 | `pendingDecisions` | 「今日あなたを待っているもの」は会社全体のもの |
| 8 | `amp pause` の「もう取り消せない投稿」 | アカウントを指定しない停止は会社全体を止める |

1〜4・6〜8 は `each()` を回す。**5だけは回せない** — 読者が待っている経路で、アカウントの
数だけクエリを撃つのは違う。

### `/go/<code>` の扱い

この経路は**もともとアカウント非依存**で、そう設計されている（`handleRegirect` は `Runtime`
ではなく「ストアとidと時計」だけを受け取る）。**コードから宛先を引くのがこの1本の仕事**であって、
アカウントの区画を覗いているのではない。

だから registry に**この用途だけの1本**を置く: `findLinkByCode(code)`。SQLでは1クエリ、
ファイルでは全ディレクトリ走査。**見つかった `TrackedLink` は `ventureId` を持っている**ので、
クリックの記録はそのアカウントのストアに入る。区画をまたぐのは「どこの誰か」を決めるまでで、
書き込みは必ず1つの区画に落ちる。

**ただし、どの区画にあったかが正で、文書の中の `ventureId` ではない。** `findLinkByCode` は
見つけた区画の名前で `ventureId` を上書きして返す。監査ログを scope で刻印するのと同じ理由で、
「これは誰のものか」の答えが2つあると、片方を信じたコードがもう片方のアカウントに書き込む。
実際にテストの仕込みデータでそれが起きた。

## 5. 移行

**SQLとファイル、両方に要る。** ファイル側を忘れると、新しい配置が古いファイルを見ないまま
空のファイルを作り、**運用者の履歴が「無かったこと」になる。エラーも出ない。** 移行の失敗の
仕方として最悪なので、両方に同じ規則を置いた。

- 設定に `ventures` が1つしか無い → 全部それに割り当てる
- 2つ以上ある → **推測しない。** 拒否して、1つだけにして1回起動させる

2つ目の分岐が存在しないうちにやるのが「今が一番安い」の中身。

**SQLは `ALTER TABLE` では済まない。** SQLite は主キーに列を足せないので、作り直して移し替える。
そしてそれは **1つのバッチ**で行う: Cloudflare では最初のリクエストと毎分Cronが別のアイソレートで
同時にここへ来ることがあり、**改名まで済んで写し替える前で止まった再構築は、履歴の消失**だから。
D1 のバッチは原子的で、バッチを持たないドライバでは順に走る（＝単一プロセスのホストでは同じこと）。

### 本番の予行演習（2026-09-10）

本番の D1 と同じ形（`PRAGMA table_info` で確認した4列、96行、10コレクション、`seq` 1〜96 の
並びまで同一）をローカルの SQLite に作って通した。

```
rows before: 96   after: 96
columns now: venture, collection, id, seq, json
cycles 3 / swipe 38 / ideas 30 / patterns 9 / posts 3 / decisions 5 / drafts 3 / inspections 3 / links 1 / clicks 1
順序: 保たれた   監査ログ: 読める   別アカウントから見える行: 0
```

監査テーブルは移行不要だった。`venture_id` 列がすでにあり、本番の30行すべてに `main` が入っている。

### 本番で通した（2026-09-10）

デプロイ後の D1 は予行演習のとおりになった。

```
records の列: venture, collection, id, seq, json
96行 / seq 1〜96 / アカウント数 1（すべて main）
swipe 38 / ideas 30 / patterns 9 / decisions 5 / cycles 3 /
drafts 3 / inspections 3 / posts 3 / links 1 / clicks 1
records_pre_split: 残っていない
```

そのうえで、**書き換えたばかりの `dispatchDue` を本番のデータで通した**: 枠を1分前に
動かすと、59秒後に毎分Cronが公開まで持っていき、監査ログに `venture_id: main` で
`post.published` が入った。アカウントをまたぐ読みが、実データの上で動いている。

## 6. 段階

各段階の終わりで `npm run check` が緑であること。

| 段階 | やること |
|---|---|
| 1 | `venture` 列、スコープ付き `createSqlStore`、`StoreRegistry`、契約テストを3実装に当てる。**済** |
| 2 | `assemble` / `runtime` が registry を持つ。オーケストレータが venture ごとに解決する。**済** |
| 3 | 4節の8つを `each()` / `findLinkByCode` に載せ替える。**済** |
| 4 | 既存データの移行（5節）とスモークテスト。**済** |
| 5 | `amp venture export` / `import`（売却のときに渡すもの。retrofit 5番の残り） |

5は別コミットでよい。1〜4で「混ざっていない」が成り立つ。
