# 探索 — アカウントを増やす判断を、機械が提案し人が決める

**状態:** 設計 → 実装済み（この文書の「実装」節に何がどこにあるかを書く）
**関連:** [要件定義](../1-requirements/requirements.md) / [複数アカウントの提案](multi-venture-architecture.md) / [用語集](../7-references/glossary.md)

## 何を足すのか

いまの製品は、**1つの運用アカウントの中**では自動で仮説を作って検証する。
リサーチ担当が型を抽出し、企画担当が根拠付きで案を出し、分析担当が実績で型を昇格・引退させる。
足りないのはその外側、**どのアカウントを持つか**の判断で、これは全部人間が `ventures[]` に手で書いている。

足すのは3つ。

| # | もの | 一言で |
|---|---|---|
| 1 | `company.principles` / `company.boundaries` | 会社の思想と、どのアカウントでもやらないこと。全役割のブリーフに入る |
| 2 | **探索担当**（7つ目の役割）と `amp scout` | 既存アカウントの実績と市場から、次に試す運用アカウントを根拠付きで提案する。週1回、人が採否を決める |
| 3 | **全アカウント一覧**（`amp portfolio` と承認画面の一節） | どのアカウントが効いているか、止まっているか、計測が閉じているかを1枚で見る |

3は2の材料でもある。探索担当が読むのは、全アカウント一覧と同じ数字。

## 変えないこと

- **人間の毎日の仕事は2つのまま。** 探索は毎日のサイクルに入らない。別のコマンド・別の頻度・承認画面でも別の節。
  日課に3つ目の判断を混ぜると「30秒で2つ決める」が壊れる。
- **役割は次に何が動くかを決めない。** 探索担当は提案を返すだけ。いつ走るか（デーモンの週次／`amp scout`）、
  採用したら何が起きるか（設定ブロックを出力する）はカーネルとCLIが持つ。
- **ガードレールはコード。** 提案が指す市場が存在するか、案件がその市場で許されているか、
  カテゴリがその市場で禁止されていないか、既存アカウントと同じニッチではないかは、モデルの答えを受けたあとコードで落とす。
- **設定ファイルは人が編集する。** 採用しても `platform.config.yaml` を書き換えない。
  コメント付きの `ventures[]` ブロックを出力し、人が貼る。生成器であって常駐エディタではない（オンボード設計と同じ判断）。
- **アカウント横断の学習は入れない。** 探索担当が読むのは**集計**（投稿数・中央値・クリック・成果・通貨別報酬・型の名前と信頼度）まで。
  個々の投稿や下書きは渡さない。提案の証拠は「Nアカウント・M本の観測」の粒度で書かせる。
  これは複数アカウントの提案3節の約束を先取りして守るため。

## 1. 思想 — `company.principles` と `company.boundaries`

```yaml
company:
  principles:
    - "売る前に役に立つ。案件の無い投稿が、案件のある投稿の権利を稼ぐ"
    - "自分がやったことだけ書く。試していないものは勧めない"
  boundaries:
    - "健康・医療・金融で、結果を断定する表現はどの市場でも書かない"
    - "読者の不安を煽って売る型は、効いても採用しない"
```

- `principles` は「どう考えるか」。`boundaries` は「何をしないか」。どちらも文章で、全アカウント共通。
- `ventureBrief` に節として入る。6役割全部が同じ文を読む（キャッシュされる前置きなので、コストは1回分）。
- 探索担当は `boundaries` に触る提案を出さないよう指示される。**ただしこれはプロンプトであってガードレールではない。**
  文章の意味を機械的に検査できないので、ここに書いたからといって `policy.prohibitedClaims` を減らしてはいけない。設定リファレンスにそう書く。
- どちらも省略可。空なら節ごと出ない。

## 2. 探索担当 — Scout

### 入力（コードが集める。モデルに探させない）

- 各アカウントの直近30日: 投稿数、中央値、クリック、成果、通貨別の確定報酬、上位3つの型（名前・種類・信頼度）、案件のカテゴリ
- 設定にある市場（言語・通貨・禁止カテゴリ）と案件（カテゴリ・対象市場・単価）
- 既存アカウントのニッチと読者（同じものを提案させないため）
- `company.principles` / `company.boundaries`

### 出力（1提案あたり）

| 項目 | 何か |
|---|---|
| `niche` / `audience` / `market` / `language` | 新しいアカウントの定義。市場は設定にあるものから選ぶ |
| `category` | 提案の主カテゴリ。市場の禁止カテゴリと照合する |
| `nameCandidates` | アカウント名の候補3つ |
| `voice` | persona / firstPerson / tone の下書き |
| `offerIds` | 設定にある案件のうち、この市場で許されているもの |
| `hypothesis` | なぜ効くと考えるか。**渡した集計を引いて書く** |
| `evidence` | 根拠にした数字の名指し |
| `risk` | 正直な失敗の仕方 |
| `firstHooks` | 最初の3本の1行目 |
| `killSignal` | 30日で何を見て「やめる」と判断するか |

### コードで落とすもの

1. `market` が設定に無い → 落とす（監査ログに理由）
2. `offerIds` のうち、存在しない・非アクティブ・`targetMarkets` に市場が無いもの → その参照だけ落とす
3. `category` がその市場で `prohibited: true` → 提案ごと落とす
4. `niche` が既存アカウントのニッチと一致（前後空白・大文字小文字を無視）→ 落とす
5. `killSignal` が空 → 落とす。やめる条件を言えない提案は、実験ではなく願望

落とした提案も**監査ログに残る**。「なぜ3件頼んで2件しか来ないのか」に答えられるように。

### 永続化

新しいコレクション `proposals`（`.amp/proposals.json`）。状態は `proposed` / `accepted` / `dismissed`。
採用・見送りは誰がいつ決めたかを持つ。

### いつ走るか

- `amp scout` — 今すぐ1回。`--count` で件数。
- デーモン — `company.exploration.enabled: true` のとき、前回から `everyDays` 経っていれば1回走る。
  前回は監査ログの `role.scout.completed` で判定する（0件でも「走った」ことにする）。
- 既定は**無効**。週に1回とはいえ、ライセンシーが知らないうちにモデルを呼ぶ機能を既定で入れない。例の設定では有効にして見せる。

### 採用したら

`amp scout accept <id>` は提案を `accepted` にし、**コメント付きの `ventures[]` ブロックを標準出力に出す**。
id は niche から作ったスラッグ、`active: false` で出す。人が貼って、文体を直して、`active: true` にして、デーモンを再起動する。
設定ファイルは書き換えない。承認画面の「採用」ボタンも同じブロックを画面に出す。

### 承認画面

「探索の提案」の節。提案ごとに仮説・根拠・リスク・最初の3本・やめる条件を開いた状態で見せ、「採用」「見送り」。
毎日の判断待ちの**下**に置く。上に置くと日課の30秒に混ざる。

## 3. 全アカウント一覧 — Portfolio

`buildPortfolio(config, store, clock, dataDir, days)` が1アカウント1行を返す。

| 列 | 出どころ |
|---|---|
| 状態 | `active` / 停止中（`paused.json`） |
| 判断待ち | 未解決の決定の数 |
| 直近サイクル | 日付・状態・次のステップ |
| 投稿数・中央値 | `computePerformance`（30日） |
| クリック・成果・報酬 | 同上。報酬は**通貨別**のまま |
| 型 | active / total |
| 計測 | `describeMeasurementChain` が閉じているか |

会社全体の合計は、投稿・クリック・成果の**件数**と、**通貨別**の報酬まで。通貨をまたいで足さない。

`amp portfolio [--days 30] [--json]` と、承認画面の `/api/portfolio` ＋「全アカウント」の節。

## レビュー — 設計段階で見つけて決めたこと

**探索担当に `RoleContext` をそのまま渡せない。** `RoleContext.venture` は必須で、探索は会社単位。
役割の契約を `Role<Input, Output, Context = RoleContext>` に広げ、会社単位の `CompanyContext`（venture 無し、`note` は `ventureId: "company"`）を足した。
6役割の型は変わらない。

**「前回いつ走ったか」を提案の有無で判定してはいけない。** 0件の回があると毎tick走る。監査ログの完了イベントで判定する。

**採用が設定を書き換えると、真実が2つになる。** オンボード設計で決めた「生成器であって常駐エディタではない」と同じ理由で、出力して貼ってもらう。
不便だが、ライセンシーの設定ファイルを機械が触るのは、それ自体が要件で決めることで、ここで滑り込ませない。

**`boundaries` を守らせる手段はプロンプトしかない。** 文章の意味は機械的に検査できない。だから `boundaries` は思想の共有であって規制ではなく、規制は `policy` のまま。
設定リファレンスにその一文を置き、`boundaries` に書いたことを `prohibitedClaims` から消さないよう言う。

**提案が案件を1つも持てないことがある。** 市場に合う案件が無ければ `offerIds` は空で出す。それは「この市場向けの案件契約がまだ無い」という情報で、提案を落とす理由ではない。

**やめる条件を持たない提案は落とす。** 実験には停止規則が要る（複数アカウントの提案4節(c)と同じ）。提案の段階で言えないなら、30日後にも言えない。

**通貨をまたいだ合計を「会社の売上」として出したくなる。** 出さない。全アカウント一覧の合計行は通貨別のまま。

**日課に混ざる。** 探索の提案を判断待ちの上に置くと、朝の30秒が壊れる。下に置き、見出しを分け、件数のバッジも分ける。

### 2周目 — 管理画面から完結させる

最初の実装は「採用したらブロックを出す。貼るのは人」だった。運用者の期待は「管理画面から出来る」なので、2つ変えた。

**採用したら設定ファイルに追記する。** 書き換えではなく**追記**。ファイルを文字列として読み、`ventures:` の行の直後にブロックを差し込む。
他の行には触らないのでコメントは全部残る。差し込んだ結果を本物のバリデータに通してから元のファイルと入れ替え、通らなければ元を残してブロックを返す。
入れ替える前に `.amp/config-backups/` に日付付きの控えを取る（設定ファイルは git 管理外なので、git は持っていない）。
`active: false` で追記するので、貼っただけでは何も動かない。「設定を機械が書き換えない」という最初の判断は、
「コメントが消える・真実が2つになる」を避けるためのものだった。追記はどちらも起こさないので、判断を変えた。

**アカウントの有効・無効を管理画面から切り替える。** 反応が無いアカウントをいつまでも残さない、しかし削除はしない。
`.amp/venture-state.json` に「運用者が切った」記録を置き、デーモンは tick ごとに読む。設定ファイルは触らず、再起動も要らない。
学んだ型・履歴・成果は全部残り、再開は1クリック。停止（`amp pause`）とは別物で、停止は緊急・全体・閉じる側に倒れる、
非アクティブは判断・1アカウント・無期限・開く側に倒れる（壊れた状態ファイルで会社全体が止まってはいけない）。

**見直し候補。** 全アカウント一覧が、そのアカウント自身の数字から「見直したほうがいい」と印を付ける。ルールは2つで、コードにある。
判断できるだけ投稿があって（`review.afterPosts`）、追跡リンクに1クリックも届いていない。または中央値が会社の中央値の半分未満（`review.belowShareOfMedian`）。
印は提案であって、勝手に切らない。切るボタンの隣に理由と一緒に出す。探索担当にもこの印は渡す。

2周目のコードレビューで直したこと（10件）:
「クリック0件」の見直し印を、計測経路が閉じていて案件があるアカウントにだけ付ける（モックや案件なしのアカウントは測れないだけ）。
採用カードが「追記しました」を無条件に出していたのを、提案に記録した追記の事実（`appended`）から出す。
非アクティブ化の案内が「予約済み」を「保留」と数えていたのを、停止と同じ「チャネル側に渡ったものは出る」の区別に直す。
追記の書き込み失敗を例外ではなく値で返す（採用は既に記録されているので、ブロックは必ず返す）。
全アカウント一覧のメモを、承認やサイクル実行の直後にも捨てる。CLIの切り替えにも監査ログを残す（監査ログは追記専用なのでロック無しで安全）。
控えのファイル名を注入された時計から作る。`isVentureActive` を唯一の定義として使う。
一時ファイル→rename の原子書き込みを1か所（`storage/atomic.ts`）に集める。
停止中でも非アクティブの切り替えを画面に出す（別の判断が別の判断の取り消しを隠さない）。

### 実装後のコードレビューで直したこと

- **採用したブロックが消える。** 承認画面は30秒ごとに読み直し、採用済みは一覧から外れるので、ブロックが読めなくなっていた。
  `accept` は二度目を拒むので取り戻す手段もなかった。採用後7日はブロック付きで画面に残し、`amp scout show <id>` でいつでも出せるようにした。
- **デーモンが動いている間、CLIの採用は失敗する。** デーモンがデータのロックを持つため。ロックは必要（デーモンの中のキャッシュと衝突する）なので、
  デーモン稼働中は承認画面から決める、と文書とログの案内を直した。
- **例の設定で `enabled: true` にしていた。** 「初期状態ではモデルを勝手に呼ばない」と矛盾する。`false` に戻し、
  デーモンからの自動実行は完了したサイクルが1つ以上あるときだけにした。数字の無い状態で走らせても、自信ありげな提案が3件出るだけ。
- **カテゴリの禁止チェックが、モデルの自称ラベルに依存していた。** 「カジノ攻略」を `entertainment` と名乗れば通る。
  `category` を列挙型（案件のカテゴリ ∪ 各市場の制限カテゴリ ∪ other）にし、構造化出力で強制する。
  完全ではない（`other` と嘘をつける）が、文字列比較の相手がモデルの自由記述である状態はなくした。最後は人が見る。
- **`amp scout acept`（打ち間違い）がモデルを呼んでいた。** 2語目があれば必ずコマンド名の一部にし、未知なら拒む。`--count` も 1〜10 に丸める。
- **同じニッチを翌週また提案する。** 重複チェックが設定の `ventures[]` しか見ていなかった。未決・採用済みの提案も「使用中のニッチ」に含め、プロンプトにも出す。
- **YAMLのスカラーを裸で出していた。** 言語コード `no` は読み手に `false` と解釈される。全部を二重引用符で出し、読み手が解釈できるエスケープだけ使う。
- **スカウトを配信の前に走らせていた。** 週1回の遅いモデル呼び出しが、分単位の投稿を遅らせうる。配信のあとに動かす。
- **全アカウント一覧を30秒ごとに計算していた。** 1アカウントのときは画面が表を隠すので、2アカウント以上のときだけ計算する。

## 要件への反映

- 要件定義 §1 に「アカウントの中の仮説は自動、アカウントを増やす判断は人。ただし候補は機械が根拠付きで出す」を足す
- §5 に 5.9 探索、§8 に接点「探索の提案（週1回）」、§9 に実装状況
- 未決事項 12（調整値を設定に）は変わらない。10（複数チャネル）と 11（承認者の識別）は探索を増やすほど効いてくるので、順番を上げる価値がある
