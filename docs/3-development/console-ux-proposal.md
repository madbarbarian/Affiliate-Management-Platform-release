## 0. 結論を先に

いまの承認画面は、**6つの節が完全に同じ見た目で縦に積まれた1本のスクロール**である。
`section { margin-bottom: 34px }`（`src/console/ui.ts:91`）と
`h2 { font-size:14px; text-transform:uppercase; letter-spacing:.07em; color: var(--muted) }`
（`src/console/ui.ts:92`）が全節に等しくかかる。つまり —

**「あなたの判断待ち」と「最近の動き」は、文字の大きさも色も太さも囲みも同一である。**

この製品でいちばん重いもの（人を待っている門）と、いちばん軽いもの（監査ログの直近12行）が、
画面の上で同じ重さを持っている。これがオーナーの言う「枠もなく」の正体で、
配色やフォントを直しても消えない。

さらに、**その1本のスクロールの真ん中に「週に1回の画面」が2つ挟まっている。**
1日の物語（今日の判断 → 今日出る投稿 → 昨日までの数字 → 会社の動き）が、
全アカウント表と探索の提案によって**真っ二つに割られている。**

そして、**その日にやることがある日と無い日で、画面はほぼ同一に描かれる。**

提案は3つの層でできている。①3つの帯に分ける（セクション）、
②判断と報告を別の見た目にする（枠）、③門の中を「推奨／そのほか」に割る。
**いちばん効くのは③である。**

## 3. この画面は何を決めさせ、何を伝えるだけか

**今日、この2つは見た目で区別されていない。**

### 決めるもの（押さなければ何も起きない）

| もの | どこ | いまの見た目 |
|---|---|---|
| ① 企画の承認 / ② 投稿の承認と順番 | `#decisions` | `<section>` に囲みなし。見出しは灰色の小文字。中のカードだけ枠を持つ |
| **あなたが投稿する番です** | `#hand-over` | `.card.handover` — **緑（`--accent`）の枠。**画面で唯一「これはあなた待ちだ」と言っている要素 |
| 探索の提案（採用／見送り） | `#proposals` | 通常のカード。既定では出ない |

### 伝えるだけのもの

予約中の投稿 ・ 全アカウント ・ 直近の数字 ・ 最近の動き ・ 更新があります。

### ここから出る3つの観察

**(a) 緑の枠の理屈は正しいのに、いちばん大事なものに付いていない。**
`ui.ts:259-265` はこう書いている — 手動投稿のカードが緑なのは
「it is the one thing on this screen that does not happen unless they do it」。
**門も同じである。**門は放っておくと日付が変わって流れる（`today.activityExpired`）。
それなのに門の節には囲みが無い。語彙は既にあるのに、規則になっていない。

**(b) 操作が、報告の見出しの下に置かれている。**
`ui.ts:424-431` は「予約中の投稿」という見出しの中に `#hand-over` を先に置く。
見出しは「機械が勝手に出す投稿」と言い、その下の1枚目のカードは
「あなたが手で出さないと何も起きない投稿」である。**見出しが中身について嘘をついている。**
（`router.ts:579-582` は「これは機械がやることではない」と正しく書いている。置き場所だけが古い。）

**(c) 空のときの `<p class="empty">` は、門・予約・型・履歴・活動で全部同じ灰色1行。**
何も無い日は、画面全体が薄い灰色の文の列になる。

## 4. 提案する情報構造

### 4.1 3つの帯

**節を6つ並べるのをやめ、3つの帯に束ねる。**帯には見出しを置き、帯ごとに見た目を変える。

```
帯A ─ 今日やること        ← あなたが動かないと止まる
帯B ─ 会社が動いていること  ← 読むだけ。機械が勝手にやる
帯C ─ ときどき見るもの      ← 週に1回／ライセンシーの用事
```

| 帯 | 節 | いまどこにあるか | なぜこの順か |
|---|---|---|---|
| **A** | 停止中（あるときだけ） | 0a（同じ） | 停止中に承認は拒否される。押して知るのは最悪（`ui.ts:1040-1042`） |
| **A** | **あなたの判断待ち** | 1（同じ） | 要件3.1で主役の仕事。`console-architecture.md:56` の「変えない」 |
| **A** | **あなたが投稿する番です** | 2の中 → **独立** | 押さなければ起きない。報告の見出しの下から出す（観察 b） |
| **B** | 予約中の投稿 | 2 | Aを終えた人の次の問い「今日は何が出るのか」 |
| **B** | 昨日までの数字 | 5 | 「昨日はどうだったか」。`Idle.dc.html` の並びと同じ |
| **B** | 最近の動き | 6 | 「機械はちゃんと動いていたか」。失敗が出る唯一の場所 |
| **C** | 全アカウント | 3 → **下へ** | `console-architecture.md:57`「週に1回」。いまBを真っ二つにしている |
| **C** | 探索の提案 | 4 → **下へ、かつ空なら消す** | 同上。既定では永久に空（§6） |

**動かした理由は1つだけ：帯Bは1日の物語で、いま帯Cがその真ん中に挟まっている。**
「今日出る投稿」を読んだ次に11列の比較表と週1の提案が来て、その先にようやく
「昨日の数字」と「会社の動き」が来る。`canvas.json:173` は「日課ではないので下」と書いた。
**判断待ちより下ではあるが、日課より下ではなかった。**

更新の通知（0b）は**動かさない。**理由は §8 に。

### 4.2 帯の見た目

```
帯の見出し   ─ --ink、15px、標準の太さ、上に1本の罫。3つだけ。
             （いまの h2 は 14px UPPERCASE letter-spacing muted — これは節の見出しに残す）
節の見出し   ─ いまのまま
```

### 4.3 判断と報告を、別の見た目にする

**規則を1つにする：あなたを待っているものは、緑の枠を持つ。**

| | 判断（帯A） | 報告（帯B・C） |
|---|---|---|
| 節の囲み | `border: 1px solid var(--accent)` ・ `background: var(--panel)` ・ `border-radius: var(--radius)` ・ padding | 囲みなし。地のまま（いまと同じ） |
| 節の見出し | 囲みの中に入り、`--ink`・太字 | いまのまま（灰色・小文字） |
| 中のカード | **自前の枠を外す。**項目の間は1本の罫 | いまのまま |
| 押すボタン | 囲みの底、主ボタンは全幅 | — |

`.card.handover` の緑枠（`ui.ts:265`）は、この規則の**先取りだった**。
規則にすれば、手動投稿のカードは例外でなくなり、門が初めて枠を持つ。
カードの二重枠（囲みの中に囲み）を避けるため、判断の節の中では `.card` の枠を罫に落とす。

**これは既存のCSSで全部できる。**新しい依存も、フレームワークも、クラスライブラリも要らない。

### 4.4 門の中に、セクションを入れる ← **いちばん効くのはこれ**

`ideasPerCycle` は**出荷される設定ファイルで 10**（`platform.config.example.yaml:491`。
スキーマの既定も10 — `src/config/schema.ts:669-674`）。つまりライセンシーの門には
**10枚の同じカードが、同じ重さで、1列に出る。**
板（`Main.dc.html`）と README（`design/README.md:65-66`）は
**最初から違うものを描いていた。**

```
あなたの判断待ち
  ├─ 推奨            ← 3件。最初からチェック済み。開いている
  │    「昨日までの実績から選びました。このまま承認できます。」
  └─ そのほかの7件を見る  ← <details>。畳んである
```

実装上の注意（提案の一部として先に書いておく）:

- `<details>` の開閉は**30秒のポーリングで閉じてはいけない。**
  この機構は既にある — `openDetails` の `Set` と `detailsKey()`（`ui.ts:817-846`）。
  **新しい仕組みを作らず、これを1段外側に伸ばす。**
- **チェックの入った案は、畳まれた側に隠れてはいけない。**
  推奨を外して別の案を選ぶのは正常な使い方で、その案が見えなくなるのは事故。
  規則：選択されている項目は常に開いている側に出す。
- `autonomy: manual` では何も事前選択されない（`router.ts:531-533`）。
  そのときも分割は有効（推奨は「印」として残り、チェックだけが無い）。
- 推奨が0件、または全件が推奨のときは**分割せず1列で出す。**
  `recommended` は役割が決めるもので、3件である保証はどこにもない。

**なぜこれがいちばん効くか。**「枠もなく、セクションもなく、わかりにくい」の3つに、
この1つが同時に答える。枠（2群が別の囲みを持つ）、セクション（門の中に初めて構造ができる）、
わかりにくさ（読む対象が10から3に減る）。そして README がその効果を**既に言葉にしている** —
「そのまま押せば30秒で終わる」。

## 8. 考えて、採らなかったもの

**(a) 更新の通知（`#update`）を帯Cへ下げる。**
`ui.ts:283-284` は「an update is the licensee's business and can wait for them to finish」
と書きながらページの最上部に置いている。矛盾に見えたので下げようとしたが、
`messages.ts:88-89` に理由が書いてあった — 「**a notice nobody scrolls to is the silence
this exists to end**」。しかも更新が無い日は `#update` は空（高さ0）で、
そもそも何も占有していない（`ui.ts:406-408`）。**払う代償が無いので、動かさない。**

**(b) 門を専用ページ（`#/decide`）に出す。**
30秒の画面としては最も純粋だが、`console-architecture.md:56` が第1階層を
「判断待ち＋予約中の投稿」と決めており、それを割ると
「今日は何が出るのか」を見るのに1クリック増える。オーナーの不満は
「画面が多すぎる」ではなく「1枚に構造が無い」なので、**枚数を増やすのは答えではない。**

**(c) 全アカウント表を `#/accounts` に独立させる。**
`#portfolio-section` は `width: min(1240px, …)` で `main` の860pxから横にはみ出しており
（`ui.ts:151`）、読み物の幅を破っているのは事実。ただし
`console-architecture.md:154-155` が第2階層を**この節として実装済みと記録**していて、
住所（`#/ventures/<id>`）は第3階層の話である。**帯Cへ下げるだけで、
「1本のスクロールが週1の画面に割られる」問題は消える。**独立は、消えなければ次にやる。

**(d) 左のサイドバーや、帯ごとのタブ。**
「枠が無い」に対する一般的な答えだが、この画面の帯Aは**週の大半が空**である。
空の箱を3つ並べて切り替えさせるのは、1本のスクロールより悪い。
それに `Idle.dc.html` は390px幅のスマホの板で描かれていて、
サイドバーはその形に入らない。

**(e) 全部の節をカード（`.card`）で囲む。**
いちばん安直な「枠を付ける」。採らない理由は、**それが問題の逆だから** —
いま全部が同じ見た目であることが問題なのに、全部を同じ囲みで包むと
「あなたの判断待ち」と「最近の動き」はまた同じ重さになる。**囲みは、
待っているものだけに与えるから意味を持つ。**

**(f) 推奨／そのほかの分割を、サーバー側（`router.ts`）で2つの配列にして送る。**
きれいに見えるが、`preselect` と `recommended` はもう送られていて
（`router.ts:533,538`）、並べ替え（`entry.order`）も選択（`entry.selected`）も
ページ側の `draft` が持っている。分割をサーバーに移すと**順序の正本が2つになる。**
表示の分割は表示の仕事にする。

**(g) 「次の判断は 6:30」をサーバーの時刻計算で厳密に出す。**
`Idle.dc.html` は「今日 07:00 ・ 企画10案」と件数まで約束しているが、
件数は走ってみないと分からない。**時刻だけを言う。**
言えないことを画面に書かせないのは、この repo が
`scout.empty` の嘘で一度払った代償である（STATUS.md 0c）。

## 11. 制約について — どれが画面を難しくしているか

ブリーフの制約を1つずつ。**難しくしている制約は1つも無い。**

- **端末が無い。** 難しくしていない。むしろ §6.2 は、その制約を守っていないことが
  画面を壊している例である。
- **文面は `messages.ts` の ja/en。** 難しくしていない。§7 の13キーは既存の形に収まる。
- **依存を増やさない・サーバー描画のHTML＋インラインCSS。**
  難しくしていない。§4 の囲み・帯・`<details>` の分割は全部いまのCSSで書ける。
  `<details>` の開閉保持の機構も**既にある**（`openDetails`、`ui.ts:817-846`）。
- **板はコードと一緒に動く。** 難しくしていないが、**いま動いていない**（§2）。
  板が3か所で実装より先を行っている状態は、次に誰かが板を信じたときに事故になる。
