# 外とつながる部分は、いまどこまで本物か

> 2026-09-12。「A8.net も Amazon も入れていないのに、これが動く気がしない」という
> オーナーの問いに答えたもの。**答えは「構造は本物、中身はまだ一つも通っていない」。**
>
> 「どう足すか」は[拡張](extending.md)にある。ここに書くのは
> **いま何がどこまで本物か**と、**本物にするとき何にぶつかるか**である。

---

## 1. 構造は差し替えられる。これは確認済み

ポートに、特定のサービスの事情が漏れていない。

```ts
// src/channels/channel.ts
discover / publish / comment / metrics / healthCheck + capabilities

// src/networks/network.ts
listOffers / fetchConversions / buildTrackedUrl / healthCheck
```

Threads の都合も A8.net の都合も、この型には入っていない。
**チャネルが Threads とは限らず、ASP が A8.net とは限らない設計になっている。**

とくに `buildTrackedUrl` は、ASPごとに計測パラメータの形が違うことを最初から
織り込んだ穴である。Amazon のアソシエイトタグも、A8.net の `a8mat` も、ここに入る。

`listOffers` が空を返してよいことも重要で、**カタログAPIを持たないASP**
（国内ASPのほとんど）は、案件を設定ファイルに宣言する経路が用意されている。

## 2. いま何が本物で、何が本物でないか

| | 状態 | 本物になったことがあるか |
|---|---|---|
| `mock` チャネル | 完動 | — |
| `webhook` チャネル | 実装済 | **無い** |
| `threads` チャネル | 実装済 | **無い。HTTPの経路を一度も通っていない** |
| `mock` ASP | 完動 | — |
| `csv` ASP | 実装済 | **無い。しかも Cloudflare では動かない（下記4）** |
| `webhook` ASP | 実装済 | **無い** |

**「実装済」と「動く」は違う。** [モックが見ていない帯域](../6-testing/bands.md)が
2026-09-10 の時点で既に「`threads.ts` はモック越しにしか通っていない」と書いていた。
この文書は、その指摘を具体的な作業に落とすためにある。

### `threads.ts` の何が確かめられていないか

`test/threads.test.ts` が触っているのは `renderParts` — 長い文章を分割して、
どの断片にも開示文が残るようにする関数だけである。**`graph.threads.net` に
POST する経路は、テストが一度も通っていない。**

このリポジトリには既に正しいやり方がある。`test/anthropic.test.ts` は
**本物のHTTPサーバーを立てて、SDKが実際に送ったリクエストの中身を読む。**
「モックのプロバイダはリクエストを一度も見ないから、この種のバグは他に
見つけようがない」という理由で追加されたもので、そこで実際に2件の400が見つかった。

**同じ手法を Threads に適用していない。** いまのままだと、ライセンシーの
最初の投稿が、そのコードが動く最初の瞬間になる。

## 3. チャネルを増やすとき

X / note / YouTube は、設定ファイルに `adapter: webhook` のひな型がコメントで
入っている。自前のサービスか Make / Zapier / n8n のシナリオに向ける形である。

**`format` が効く。** 280字の投稿と note の記事は、同じ文章の長さ違いではなく
別の仕事なので、ライティング担当の出力そのものが変わる（`short` / `thread` / `longform`）。

**`capabilities` で「できないこと」を宣言できる。** コメントを書けないチャネル、
数字を返さないチャネルがあっても、役割の側を変えずに済む。

## 4. ASPを増やすとき — ここに本当の穴がある

### Cloudflare では `csv` アダプタが動かない

```
src/networks/csv.ts:19  import { readdir, readFile } from "node:fs/promises";
```

CSVアダプタはファイルシステムを読む。**Cloudflare Workers にファイルシステムは無い。**
そして要件3.1は「ライセンシーは端末を持たない」と決めている。

**つまり Cloudflare で動かしているライセンシーは、国内ASPの成果を1件も取り込めない。**
A8.net も、もしもも、バリューコマースも、成果レポートはCSVで落とす方式である。

これは設定の問題ではなく、**設計の穴**である。既定の置き場所を Cloudflare に
寄せる判断（未決事項15）をしたとき、この帰結が検討されていない。

**要件3.1の規則がそのまま当てはまる:**
「配布方法・実行環境を変える判断は、必ずこの表に戻る。」

考えられる形は3つある。どれを採るかは決まっていない。

| 案 | 中身 | 気になる点 |
|---|---|---|
| A | 承認画面にCSVをアップロードする欄 | ライセンシーが月1回、自分で落として上げる。端末は要らない |
| B | ASPのAPIを叩くアダプタ | 国内ASPで公開APIを持つところは少ない。要調査 |
| C | メール転送を受ける | 成果レポートのメールを解析する。取りこぼしが読めない |

### Amazon アソシエイトは、ASPというより「開業届」である

> 2026-09-17。「Amazonアフィリエイトってどうやるの？」への調べ物から。
> **ここは制約ではなく、前提条件の話である。**

A8.net が「案件に応募して提携する」のに対し、Amazon は商品URLに自分のタグを
足すだけで、提携という手続きが無い。そのかわり**参加そのものに条件がある**。

**登録しただけでは審査が始まらない。** 登録から180日以内に、自分のリンク経由で
**他人が3件買う**ことが審査の受験資格になる。自己購入は数えず、家族・友人に
頼むのは規約違反。1回の注文に3商品入れても1件である。

**つまり Amazon は「読者がいる人」向けの制度で、初日には使えない。**
A8.net が「審査に通れば読者0人でも案件を持てる」のと逆の順番になる。
最初のライセンシーに「アフィリエイトを登録してください」と言うとき、
**A8.net と Amazon は同じ日にできる作業ではない**。

**紹介料の発生条件も他と違う。** クッキーは24時間。ただし24時間以内に
カートへ入っていれば、カートが生きている間（通常90日）は成果になる。
そして**リンク先の商品でなくてよい** — 本のリンクから入って洗剤を買っても
紹介料になる。1商品あたり1,000円だった上限は2024年8月に撤廃された。

#### 日本と米国は、別のプログラムである

ライセンシーが日米どちらも視野に入れる場合、ここが効く。

| | Amazon.co.jp | Amazon.com |
|---|---|---|
| 登録 | 個別に申請 | 個別に申請 |
| **3件の壁** | 180日で3件 | **もう一度、180日で3件** |
| タグ | `-22` | `-20` |
| 支払い | 別勘定 | 別勘定。日本在住者は米国の税務書類が要る |

**3件の壁が2回ある**のが実務上いちばん重い。読者が日本に偏っていれば、
米国側の3件はいつまでも埋まらない。

Amazon 自身が **OneLink** という仕組みを持っていて、アソシエイト・セントラルで
各国のアカウントを紐づけておくと、リンクを踏んだ人をその人の国の Amazon へ
正しいタグ付きで送ってくれる。ただし**紐づける先には先に登録して通っている
必要がある** — 審査を省く道具ではなく、通ったあとの配線である。

**[越境の設計](../7-references/cross-border.md)とは衝突しない。** 市場が2つなら
アカウントを2つ作る（`ventures:` に `jp_main` と `us_main`）という形は変わらず、
Amazon 側の条件が2倍になるだけである。通貨を足さない設計はここで報われる。

#### 対象SNSに Threads が入っていない可能性がある

Amazon アソシエイトは、紹介するサイト・SNSアカウントを**1つずつ申告する**方式で、
ブログで通った審査がそのまま SNS に及ぶわけではない。案内されている対象SNSとして
繰り返し挙がるのは **X・Facebook・Instagram・YouTube・Twitch** で、
**Threads は挙がっていない。**

**これは二次情報である。** 公式の `affiliate.amazon.co.jp` は開発環境の
ネットワーク制限で直接読めなかった。確認は実アカウントの登録画面を開いて、
**SNSの選択肢に Threads があるか**を見れば済む。

事実なら、既定のチャネルが Threads であることと Amazon が**両立しない**。
`threads` チャネルは残したまま、Amazon を扱うライセンシーには X などの
対象SNSを併用してもらうことになる。**確認前に設計を変えない。**

### Amazon アソシエイトには、構造と別の制約がある

**運営規約がリダイレクトによる隠蔽を禁じている。**
Amazon が「どのサイトから来たクリックか」を判別できなくなる形、および
読者に「Amazonへ行く」ことが分からなくなる形が対象である。

このプラットフォームは**全てのリンクを `/go/<code>` に通す**。
ASPを乗り換えても過去の投稿が死なないための設計で、それ自体は正しい。
だが Amazon に対しては、そのままだと次の2点が問われうる:

- 読者から見て、`/go/abc123` が Amazon 行きだと分からない
- クリックの参照元が、投稿したSNSではなく自分の workers.dev ドメインになる

**これは法務判断であり、私が決めることではない。** 考えられる対応は
「Amazon だけリダイレクトを経由せず直リンクにする」（計測は Amazon 側のタグに任せる）
だが、それは「計測はこちらが持つ」という設計の一部を Amazon に対してだけ降ろすことを
意味する。**採否は未決事項として扱う。**

出典: [Amazon アソシエイト・プログラム運営規約](https://affiliate-program.amazon.com/help/operating/policies)

## 5. 先に確かめるべきことの順番

**資格情報がゼロのまま確かめられることが、まだ一度も人に試されていない。**
[オンボード設計](../2-setup/onboarding.md)が「鍵を1つも持たずに製品が動くところまで
行けること」を第一原則に置いているのは、このためである。

| 順 | 何を | なぜ先か |
|---|---|---|
| 1 | 模擬モードで、最初の1時間と最初の3日を人に試してもらう | 貼り付けが本当に脱落点か、案が読むに値するかは、鍵が無くても分かる |
| 2 | `threads.ts` を偽のHTTPサーバー相手に検証する | 一度も動いたことのないコードで実アカウントに投稿すると、失敗の切り分けができない |
| 3 | Cloudflare での成果取り込みを決める（上の A/B/C） | ASPの審査に数日かかるので、並行して進む |
| 4 | Amazon の登録画面で、対象SNSに Threads があるか見る | **5分で済み、事実なら既定のチャネルと両立しない。**登録は無料で、ここまでに費用も判断も要らない |
| 5 | Amazon の扱いを法務判断する | 3の形が決まらないと、具体的な問いにならない |

**Amazon を「最初のASP」に据えないこと。** 3件の壁（上の4節）があるので、
読者ができる前に登録しても180日で失効する。順番は A8.net で案件を持つ →
読者ができる → Amazon を足す、である。

**2を飛ばして実アカウントに投稿しないこと。** 失敗したときに
「製品が悪いのか設定が悪いのか」が切り分けられず、最初のライセンシーの信頼を
一度で失う。
