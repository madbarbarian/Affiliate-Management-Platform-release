# 承認画面をどう分けるか — 俯瞰と、1アカウントの中

> **1〜3は実装済み**（2026-09-09〜10）。4はロールと割り当てで、**保留**。
> 保留の判断と、運用担当者とテナントの見分け方は [人を増やす](adding-people.md)。
> 要件の [未決事項 11・12・16](../1-requirements/requirements.md#10-未決事項)、および
> [複数アカウントの提案](multi-venture-architecture.md) の retrofit 順の 2 番と直結する。

## 1. いま何が起きているか

承認画面は1本のスクロールで、上から順にこうなっている。

```
あなたの判断待ち     ← 今日の仕事
予約中の投稿         ← 今日の仕事
全アカウント         ← 週に1回
探索の提案           ← 週に1回
直近の数字           ← 全アカウント合算
最近の動き           ← 全アカウント混在
```

**全部が「全アカウント」の視点で、1つのアカウントの中に入る場所がない。** その結果、
アカウント固有のものが横に伸びる一覧の中へ押し込まれていく。直近の実例が2つある。

- 失敗の理由（API のエラー全文）を 直近サイクル の欄に入れたら、1セルが表を占領して
  他の9列が1文字幅になった。列幅を宣言して凌いだが、**そもそも一覧に置く情報ではない。**
- 「今日のサイクルを動かす」を行に足した。押した結果（承認待ちになった、失敗した）を
  出す場所が行の中にしかなく、一覧が操作盤を兼ね始めている。

一覧の仕事は**比べること**で、アカウントの画面の仕事は**そのアカウントを理解して直すこと**。
目的が違うものを1枚に載せているので、片方を良くすると片方が壊れる。

## 2. 何を参考にしたか

- **段階的開示（progressive disclosure）。** 詳細を1段下げてよいのは、それを必要とする人が
  2割を切るとき。過半が必要とするなら、隠さず上げる。逆に、よく見る画面に操作を足しすぎると
  「見て分かる」までの時間がかえって伸びる、という2026年の測定がある
  （[Setproduct](https://www.setproduct.com/blog/dashboard-ui-design)、
  [Improvado](https://improvado.io/blog/dashboard-design-guide)）。
- **Buffer** はアカウント（チャネル）を切り替える形、**Hootsuite** は組織とチームを作って
  そこに人を割り当てる形。どちらも「全体を見る画面」と「1つを扱う画面」は別で、
  設定はアカウント側にある（[Zapier の比較](https://zapier.com/blog/hootsuite-vs-buffer/)、
  [Buffer のレイアウト解説](https://support.buffer.com/en-us/articles/navigating-buffers-new-dashboard-layout-JsRJX4s6QQ)）。
- 設定の保存は**節ごと**が推奨されている。全体に1つの保存ボタンを置くと、何が保存されるのかが
  利用者から見えない（[UX Patterns](https://uxpatterns.dev/patterns/authentication/account-settings)）。
  この製品では設定はYAMLなので直接は効かないが、「アカウントの設定はアカウントの画面で」
  という結論は同じところに着く。

**この製品に固有の重み。** 運用者の1日は2回の判断で終わるという約束がある。だから
第1階層は俯瞰ダッシュボードではなく「今日やること」でなければならない。一般的な
ダッシュボード論をそのまま持ってくると、ここを間違える。

## 3. 提案する3階層

> 🔴 **訂正（2026-09-23、[決定記録](../5-project-management/decisions.md)の
> 「2026-09-23 トップ画面から判断待ちを外す（複数アカウント前提へ）」）。**
> 下の表の第1階層は「判断待ち、予約中の投稿。**変えない。ここが今も正しい**」と書いていた。
> **これを覆した。** 前提が変わったからである — あの記述は「毎日30秒で終わる」を守るためのもので、
> **1アカウントなら正しかった。** オーナーが3アカウントを実際に運用した上で「複数アカウント前提です」
> （2026-09-23）と決めたことで、逆に働き始めた：3アカウントぶんの判断が section も無い1本のリストに
> 混ざり、「わかりにくい」という指摘を生んだ。
>
> **いま第1階層に置くのは、アカウントごとの状態（承認が要る／いま投稿する番です／失敗しています）
> だけ。** 判断待ち・予約中の投稿・手渡しの投稿カードは、すべて第3階層（各アカウントの画面、
> `#/ventures/<id>`）へ移した。実は第3階層はもとから1アカウントに絞って判断待ちを出していた
> （`state.pending` をそのアカウントで filter していただけ）——トップがそれと同じものを
> もう一度、全アカウント分まとめて出していたのが元の欠陥だった。
>
> 元の記述は消さず、下の表にそのまま残す。**なぜ一度そう決めたかは、次に「1アカウントに戻すべきか」
> という問いが来たときに効く。** 実装は `feat: make the top page account status only, move
> judgement to each account`（v0.12.0）。バッジが実際の判断待ち件数と一致することを検査する
> テストの要求（決定記録の条件2）は `test/console.test.ts` の
> 「the status strip's numbers match ground truth read independently of /api/state」で満たした。

| 階層 | 画面 | いつ見るか | 置くもの |
|---|---|---|---|
| 1 | **今日** | 毎日30秒 | ~~判断待ち（①企画・②投稿）、予約中の投稿。**変えない。** ここが今も正しい~~ 🔴 **2026-09-23 に覆した（上記）。** いま置くのはアカウントごとの状態（承認が要る／いま投稿する番です／失敗しています）、全アカウント合計の数字、最近の動き、探索の提案。判断待ち・予約中の投稿・手渡しの投稿カードは第3階層へ |
| 2 | **全アカウント** | 週に1回 | 比べられる数字だけ。状態・投稿・中央値・クリック・成果・確定報酬・型・計測。行を押すと3へ |
| 3 | **アカウント** | 何かあったとき | そのアカウントの全部。**判断待ち・予約中の投稿・手渡しの投稿カード**（2026-09-23 にここへ移した）、サイクルの履歴と失敗の理由、プレイブック、案件とチャネル、市場と開示、非アクティブにする／今日のサイクルを動かす |

**第2階層から操作を抜く。** 一覧に残る操作は「開く」だけにする。非アクティブにする・
今日のサイクルを動かすは第3階層へ移す。一覧が操作盤を兼ねるのをやめれば、列は数字に戻り、
横幅の問題は設計として消える（今の列幅の宣言は、それまでの対症療法）。

**失敗だけは例外にする。** 一覧の 直近サイクル に「**実行できませんでした**」と、その下に
小さく1行の補足を出す。理由の全文はアカウントの画面。失敗は稀だが緊急で、隠すと気づくのが
翌週になる——実際にそうなった。これは段階的開示の2割ルールの、正しい方の例外。

**同じことが 最近の動き にも要る。** 一覧の 直近サイクル は「今どうなっているか」で、
最近の動き は「何が起きたか」。失敗はどちらにも出す。実際、監査ログに失敗が1行も
入っていなかったせいで、2日ぶん死んでいる間ずっと 最近の動き は「まだ記録がありません」
と言っていた。**記録が無いことと、何も起きていないことは、画面の上で見分けがつかない。**

**その要約は失敗のコードから作る。** `write.all_failed` →「実行できませんでした」、
`inspect.unreadable` →「検品できませんでした」。APIのメッセージを切り詰めて作ってはいけない：
先頭が英語だったり、途中で切れて意味が反転したりする。訳の無いコードが来たらコードそのものを
出し、`src/console/labels.ts` と同じくテストが落ちる形にする。

**第3階層の住所。** 今の承認画面には経路（ルート）がない。`#/ventures/<id>` を導入する。
ハッシュにするのは、ワーカーでもデーモンでも同じ1ファイルのままで済むから。

**アカウントの設定は読み取り専用で見せる。** 編集はYAML（それがこの製品の約束）。
ただし「今このアカウントに何が効いているか」——ニッチ、読者、声、市場、開示文、案件、
チャネル、投稿頻度——が1枚で読めないのは、設定ファイルを開かせているのと同じ。
どのファイルのどの行かを添えて表示する。

## 4. 言語（日本語／英語の切り替え）

未決事項 12 が「承認画面の言語（日本語のみ）」を、自分たちの原則違反として挙げていた。
**済**（2026-09-10）。文字列は `src/console/messages.ts` に ja / en の2本で入り、
`console.locale` が選ぶ。`en` は `Record<keyof typeof ja, string>` なので、片方にだけ
足したキーはコンパイルエラーになる。

**画面の半分はサーバが描いている、というのを忘れないこと。** 承認ゲートの見出し・質問、
指摘や予測のチップ、直近の数字のラベル、下書きのプレビューの項目名は `router.ts` が作る。
ここを直書きしていたせいで、`locale: en` は英語の外枠の中に日本語のゲートを出していた。
`router.ts` も同じ `messages.ts` を読む。**語彙は1つ。**

**モデルが書いたものは、画面の言語に従わない。** 下書きも、そのリスクの一文も、
読者の市場の言語で書かれている。英語で画面を使っていても本文は日本語のまま出る。
翻訳してはいけない（それは読者に出る文章だから）。

**これだけは混ぜてはいけない。** 画面の言語と、**開示・規制の言語は別物**。開示は読者の市場が
決める（`src/domain/market.ts`）。英語で画面を使う日本市場の運用者に、英語の開示文を出しては
いけない。CLAUDE.md の「コンプライアンスは広告主ではなく読者に従う」がそのまま効く。

## 5. 人を増やす — 今どうなっていて、何が高くつくか

> **決定は [人を増やす](adding-people.md) にある。** この節は調査で、あちらが結論。
> 先に読むのはあちら。

**結論：実装は無い。要件が明示的に「やらない」と書いている**
（[要件 11節](../1-requirements/requirements.md#11-意図的にやらないこと)：複数人での同時運用）。
ただし未決事項 11 と、複数アカウント提案の retrofit 順の 2 番が、これを「後から直すのが高い」
側に置いている。実際に何が無いのか：

- **合言葉は1つ。** URL とトークンを知っている人は全員、同じ全権の運用者。区別が無い。
- **`decidedBy` は型にも監査ログにもあるが、入るのは `company.operator` の文字列か `"auto"`。**
  つまり「誰が承認したか」は記録される形をしていて、中身が識別子になっていない。
- 利用者の登録も、招待も、アカウントへの割り当ても無い。
- 契約は3階層（ライセンサー／ライセンシー／テナント）だが、**それは契約上の階層であって、
  画面を触る複数人ではない**と要件が明記している。ソフトウェア側にその概念は無い。

**高くつく理由は監査ログにある。** 承認の記録は後から作り直せない。今日「owner」と書いた行は、
来年 identity を入れても「owner」のままで、誰だったかは永久に分からない。ライセンシーの知人が
運用を始めた時点で、この記録は「2人のうちどちらか」になる。

**だから、今のうちにやる価値があるのは1つだけ。** ロールも招待も要らない。
**名前つきの合言葉を複数持てるようにする。** `AMP_CONSOLE_TOKEN` を1本の秘密ではなく
「名前 → 合言葉」の対応にし、認証が通った名前を `decidedBy` に入れる。

- 利用者から見て増える手間：ゼロ（1人なら今と同じ1本）
- コード：`authorised()` が真偽値ではなく名前を返し、それが承認の記録に流れるだけ
- 効果：**運用者が2人になった日から、監査ログが本当のことを言う**

ロール（owner / manager / viewer）とアカウントへの割り当ては、その後でよい。順番はこう：

1. 名前つきの合言葉 → `decidedBy` が本物になる（**小さい。今やる価値がある**）
2. ロール3種と、アカウントへの割り当て（中。テナントを置くなら必須）
3. 利用者の登録・招待・パスワード（大。**SaaS 化を決めてから**。今の製品はライセンシーが
   自分のインフラに置くフォークで、そこに利用者データベースを足すのは別の製品を作ること）

3をやらない限り「ユーザー登録」は無い、というのは弱点ではなく、この製品の形そのもの。
そこを変えるなら、契約の階層（[licensing.md](../1-requirements/licensing.md)）から見直しになる。

## 6. 決まったこと（2026-09-09）

- 一覧から操作を抜く。残るのは「開く」だけ。**採用**
- 失敗の1行は「実行できませんでした」＋小さい補足。**採用**（3節に反映）
- 設定はアカウント画面と分けて1枚にする。**採用**

## 7. 順番と、いまどこまで

1. **名前つきの合言葉**（5節）。**済** — `console.operators`、`decidedBy` が本物に
2. **アカウントの画面**（3節の第3階層）と、一覧からの操作の移動。**済** — `#/ventures/<id>`、
   `GET /api/ventures/:id`、一覧に残る操作は「開く」だけ
3. **メッセージのファイル化**（4節）。**済** — `src/console/messages.ts` に ja / en、
   `console.locale` で選ぶ。`en` は `Record<keyof typeof ja, string>` なので、
   片方にだけ足したキーはコンパイルエラーになる
4. ロールと割り当て。**保留**（2026-09-10）。テナントは実装しない。運用担当者の
   ロールは作るが、ストアのアカウント別分割のあと。判断の根拠、崩れたらやり直す条件、
   運用担当者とテナントの見分け方は [人を増やす](adding-people.md) に。**この件に触れる前に読む**

1と3は利用者から見てほぼ何も変わらない。2を先にやると3の書き直しが増えるので、
2と3は同じ変更でやった。
