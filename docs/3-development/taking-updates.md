# 更新を受け取る — 判断

> 2026-09-11。[要件](../1-requirements/requirements.md) 3.1「ライセンシーは端末を持たない」の帰結。
> **配布・更新・リリース経路に触れる前に、この文書を読む。** 決めたことを述べるのであって、
> ここから推論をやり直さない。判断は開き直せるが、事故で開き直すのは別のことである。

## 1. 問い

**プラットフォームの修正を、端末を持たないライセンシーがどう受け取るか。**

問いは1つに見えて2つある。混ぜたまま設計して失敗した。

| | 何か | 制約 |
|---|---|---|
| **気づく** | 修正が出ていること、自分の運用に何を意味するか | **経路に依存しない** |
| **当てる** | 実際に自分の配置を新しくする | **経路が全部を決める** |

**更新があるのを知らない人は、知っていて手間がかかる人より危険である。** 前者は直っている不具合を踏み続け、
気づく契機を持たない。だから「気づく」を先に、無条件に満たす。要件の6節に非機能要件として格上げ済み。

## 2. 選べないこと

未決事項15の答えが Cloudflare である以上、動かせない。

> **Workers Builds はライセンシーの git リポジトリからデプロイする。したがってコードの変更は、
> 必ず彼らのリポジトリのコミットにならなければならない。**

「更新を当てる」＝「彼らのリポジトリに書き込む」。書き込める主体は4つしかない。

| 書き込む主体 | 必要なもの | 状態 |
|---|---|---|
| ライセンシー本人 | ブラウザ | **使える** |
| GitHub のフォーク同期 | フォークであること | **使えない** — ボタンが作るのは複製 |
| 彼らのリポジトリ内の Action | ワークフローが届いていること | **使えない** — 下記3 |
| 私たちがホストする GitHub App | 彼らのリポジトリへの書き込み権限 | 使えるが**却下**。下記4 |

## 3. なぜ Action が使えないか

`release-assets/take-updates.yml` を書き、リリースに `.github/workflows/take-updates.yml` として配り、
公開リポジトリに届いたことをログで確認した（`create mode 100644`）。そのうえでボタンを押したコピーには、
**ワークフローが1つも無かった**（Actions タブが "Get started with GitHub Actions"）。

理由として最も確からしいのは、GitHub が **GitHub App による `.github/workflows/` 配下の作成・更新に
`workflows` 権限を要求する**こと。Cloudflare の App がそれを持たなければ push 自体が拒否されるので、
ワークフローを除いて複製するほかない。**だとすれば Cloudflare 側の制約で、こちらのリポジトリを
どう直しても越えられない。**

> **未確認:** `.github` ごと落ちるのか、`workflows` だけかを確認していない。前者なら置き場所の
> 工夫は一切効かない。後者なら `.github/` 直下は使える。5節の案Bの手数が変わるだけで、
> 判断の形は変わらない。
>
> **→ 確認不要になった**（2026-09-11）。配布場所をリポジトリのルート（`update-workflow.yml`）に
> したので、どちらであっても届く。`.github` に賭けない。

### 同じ制約が、ワークフロー自身にも効く

実装して分かった。**`GITHUB_TOKEN` も `.github/workflows/` に書けない。** 権限の名前は
`workflows` で、Actions の `permissions:` には存在しない。つまり `take-updates.yml` は、
**自分自身を追加することも更新することもできない**。しかも push は1ファイルでも拒否されれば
全体が失敗するので、更新の中にワークフローが1つ混ざっただけで、**他の修正も全部道連れになる**。

だから rsync は `.github` を除外する。そのうえで現行のテキストはルートの `update-workflow.yml`
として必ず届くので、**手でやる必要が残る1点を、黙って失敗させるのではなく知らせる**。

### そして、配られていた版は YAML として不正だった

ヒアドキュメントの終端は行頭になければならず、行頭の行は YAML のブロックスカラーを終わらせる。
GitHub に届いていたとしても「Invalid workflow file」と表示されるだけだった。**3重に壊れていた**
（届かない・書けない・読めない）。

テストが気づかなかったのは、全部が文字列一致だったから。**読み込めないファイルの中でも文字列一致は
成功する。** いまは `src/config/yaml.ts`（自前のリーダー、依存を増やさない）で実際に解析し、
`gh pr create` の段が解析後も残っていることまで確かめる。配られていた版でこのテストは赤くなる。

## 4. 却下した案 — 私たちがホストする GitHub App

ライセンシーは1クリックで済み、両方の経路で動き、私たちが全部を制御できる。**それでも採らない。**

この製品の前提は「ライセンシーが自分の手元にあるものを監査する」（要件6節「依存の少なさ」）。
**私たちが全ライセンシーのリポジトリに恒久的な書き込み権限を持つことは、その前提を裏返す。**
彼らが監査したはずのコードに、いつでも私たちが書ける。契約書にもその旨を書く必要が出るし、
書けば「フォークして自分で持つ」という2階の価値が減る。

利便性と引き換えに、製品が売っているものを削る取引なので、採らない。

**この判断をやり直す条件:** ライセンシーの側から「勝手に更新してほしい」と要望が出たとき。
そのときは App ではなく、**ライセンシーが自分で発行したトークンを自分の Cloudflare に置く**形を先に検討する
（権限が彼らの手元に残り、いつでも剥がせる）。

## 5. 残る案

### 案A — 気づかせるだけ。当てるのは押し直し

Worker が更新の有無を承認画面に出す。当てるときは、**ボタンをもう一度押す**。
D1 は既存のものを選べるので、**データは残る**。

- **仕組み:** 「気づく」だけ。追加の配布物ゼロ
- **費用:** 押すたびにリポジトリと Worker が増える。設定（`platform.config.yaml`）を新しい複製に貼り直す必要がある
- **正直な評価:** 更新が年に数回なら成り立つ。月に1回なら成り立たない

### 案B — 更新の受け取り口を、初日に1回だけ置いてもらう **【採用・実装済 2026-09-11】**

ワークフローを**リポジトリのルート**（`update-workflow.yml`）でも配る。`.github/workflows/` にも同じ
バイト列を置くので、clone / fork で来た人はそのまま動く。ライセンシーは初期設定の流れの中で、
GitHub の画面で **Add file → Create new file**、名前を `.github/workflows/take-updates.yml` にして中身を貼る。
以降は Actions のボタン1つ、または月1回の自動実行で、**自分のリポジトリにプルリクエストが立つ**。

- **仕組み:** 配布場所の変更（実装済のワークフローはそのまま使える）＋オンボーディングに1手順
- **費用:** ライセンシーの初日に1手順。ただし**初日は元々ウィザードを通る**ので、他の手順と並ぶだけ
- **効く点:** 置いたワークフロー自身も以後の更新に含まれるので、**1回置けば古くならない**

### 案C — フォークを玄関に戻す

`Sync fork` が使え、仕組みが一切要らない。**ただし要件3.1の決定を覆す。** ライセンシーは Cloudflare の
ダッシュボードで Worker を作り、リポジトリを繋ぎ、D1 を作ってバインドすることになる。
端末を持たない人に、これを初日にやらせる判断である。

## 6. 決定

**気づく = 無条件に作る（案A の前半）。当てる = 案B。**

理由:

- **「気づく」は経路に依存せず、権限も git も要らない。** 判断を待つ理由がないので、他と切り離して先に満たす。
  **実装済**（v0.3.0、2026-09-11）— 承認画面の最上部の1行。これが無いことが、長らくいまの最大の欠陥だった
- **案B の1手順は、初日にしか発生しない。** そして初日はウィザード（作ることは要件3.1で決定済）を通る前提になったので、
  手順が1つ増えることの限界費用は小さい。以後は「Run workflow を押す」か、月1回のプルリクを読むだけ
- **案A 単体を採らない理由:** 押し直しは設定の貼り直しを伴い、複製が増える。
  月次の修正を運ぶ手段として成立しない
- **案C を採らない理由:** 要件3.1を覆すため。覆すなら配置・診断・更新の3つを同時に設計し直すことになり、
  更新1つのために払う代価として大きすぎる

## 7. 判断をやり直す条件

どれか1つでも起きたら、この文書は古い。

- **Cloudflare の Deploy ボタンがワークフローを運ぶようになった**（`workflows` 権限を取得した）→ 案Bの手順が消える。
  そのときは配布場所を `.github/workflows/` に戻すだけでよい
- **Cloudflare が既存リポジトリ（フォーク）への接続でも資源を払い出すようになった** → 案Cが端末なしで成立する。
  フォークが玄関になり、この文書ごと不要になる
- **要件3.1が「端末を持つ」に変わった** → 案Cが既定。この文書の前提が消える
- **ライセンシーから「自動で更新してほしい」と要望が出た** → 4節の却下をやり直す。ただし App ではなく
  ライセンシー側トークンから検討する
- **3節の未確認（`.github` ごと落ちるのか）が「ごと落ちる」と判明した** → 案Bの配布場所を `.github/` の外にする。
  判断は変わらない
