# 契約体系と責任分担 — 討議資料

**対象:** プラットフォームオーナー、法務
**状態:** 討議中。ここに書いたものは**法務の確認を受けていない**。ひな型は `contracts/` にあり、すべて草案
**関連:** [要件定義 §5.8](requirements.md) / [運用モデル](operating-model.md) / [用語集](../7-references/glossary.md) / [複数アカウントの提案 §6](../3-development/multi-venture-architecture.md)

## 1. 何を決める文書か

このソフトは、ライセンシーの SNS アカウントで、ライセンシーの ASP 契約のもとに、**自動で文章を書いて公開し、報酬を受け取る**。
契約で決めなければならないのは、突き詰めると3つ。

1. **誰が「発信者」か。** 公開された投稿の責任は誰のものか。
2. **ライセンサーは何を約束し、何を約束しないか。** コードは現状有姿か、更新は義務か、サポートはあるか。
3. **お金がどう流れ、契約が終わったら何が残るか。** 料金、データ、アカウント、フォークしたコード。

参考にした体系は、別プロジェクト（Fundraising）で使った**3階建ての契約スタック**。
1階の開発者は受動的なIP保有者に徹し（現状有姿・労務なし・対価はフィードバック）、2階の運営会社が商業活動と顧客対応を担い、3階の利用者は責任上限つきの利用規約に同意する。
支配権が変わると2階の権利は自動で消える。この骨格は流用できる。
ただしこのソフトには、あの体系が想定していなかった論点が5つある（3節）。

## 2. 登場人物と契約の線

```
[3階] テナント（ライセンシーの環境で自分のアカウントを運用する事業者）
   ▲  契約C: テナント利用規約 — サインアップ時に同意
[2階] ライセンシー（リリースリポジトリをフォークして運用する会社）
   ▲  契約B: マスターライセンス契約 — 署名。フォークを許す契約
   ▲  契約A: 先行利用許諾 — 正式リリース前の少数に、Bの代わりに
[1階] ライセンサー（著作権者）

線の外にいる人:
  読者        契約の当事者ではないが、開示・断り書き・越境の注意はこの人のためにある
  ASP／チャネル  ライセンシー（またはテナント）と直接契約している。ライセンサーは無関係
  アカウントの買い手  将来。契約D（事業譲渡）。今は決めない（6節）
```

## 3. 参照した体系と違うところ

| 論点 | 参照体系（汎用Webテンプレート） | このソフト |
|---|---|---|
| 何を配るか | 画面の骨格。設定とブランドだけ変えて使う | **自律的に公開行為をするソフト。** 配った先で毎日、法規制の対象になる文章が世に出る |
| 生成物 | 無し、または補助的 | **主成果物が AI 生成の文章。** 誤り・他人の文との類似・規制違反の可能性を、契約で誰が引き受けるか |
| 人の関与 | 常に人が操作 | `autonomy: auto` では**誰も読まずに公開される。** その選択を誰がしたかを契約に書く |
| 規制 | 一般的な消費者保護 | **景表法・ステマ規制（日本）、FTC（米国）、越境。** 読者の国で決まる。設定 `markets:` の中身が正しいかは人の仕事 |
| 資産の売却 | 会社の M&A のみ | **育ったアカウント単体の売却**が製品の想定シナリオ（提案 §6）。ライセンスは付いていくのか |
| 改造 | コアの改造は禁止 | `extending.md` が7つ目の役割の追加を**推奨**している。禁止と矛盾する |
| データ | 運営会社のサーバに集約 | **ライセンシーの手元に素の JSON。** ライセンサーは何も持たない。逆に、ライセンサーがフィードバックで何を受け取るかを決める |

## 4. 責任分担 — 誰が、何で守るか

「コードで守る」「設定で守る」「人が守る」の3つに分けて、担当を置く。
契約の責任条項は、この表と一致していなければならない。ソフトが実際にやっていないことを契約で約束しない。

| 事項 | 守り方 | 担当 | ソフト側の根拠 |
|---|---|---|---|
| 開示（PR表記）が案件つき投稿に入っていること | コード | ライセンサー（仕組み）／ライセンシー（結果） | `policy.ts` が書き直し前後で文字列検査。承認画面で赤表示 |
| 禁止表現・断り書き・文字数 | コード | 同上 | 同上 |
| **市場ルールの中身**（開示文言、禁止表現、禁止カテゴリ） | 設定 | **ライセンシー** | `markets:`。例の値は出発点で法的助言ではない（LICENSE に明記済み） |
| ASP の契約範囲（許可された国・表現・媒体） | 設定 | **ライセンシー** | `offers[].targetMarkets` / `complianceNotes`。範囲外は起動時に拒否 |
| チャネル（Threads 等）の規約・自動化ポリシー | 人 | **ライセンシー** | ソフトは検査しない |
| 公開された投稿の内容（AI生成を含む） | 人 | **ライセンシー**（テナント運用なら**テナント**） | 承認①②は人の判断。`auto` はその放棄を選んだ記録が `decisions` に残る |
| `auto` で誰も読まずに公開すること | 人 | 選んだ者 | 設定値と `autoResolved` の記録 |
| 資格情報（トークン・APIキー）の保管 | 人 | ライセンシー | `.env.local` のみ。ソフトは他所に送らない |
| 運用データの保管・バックアップ | 人 | ライセンシー | `.amp/` は素の JSON。ライセンサーは一切持たない |
| 計測経路が閉じていること | 設定＋人 | ライセンシー | `doctor` が `measurement:` で言う。止めはしない |
| モデル利用料（Anthropic） | 人 | ライセンシー | ライセンシー自身のキー。ライセンサーは請求経路に入らない |
| コードの欠陥 | — | **誰も保証しない**（現状有姿） | ライセンサーは修正義務を負わない。直したものは配る |
| 法令・規制の変更への追従 | 人 | ライセンシー | ソフトは「書かれたルール」しか知らない |
| セキュリティ上の問題の連絡 | 人 | 相互に努力義務（保証ではない） | 先行利用ではフィードバックの一部 |
| アップデートの適用 | 人 | ライセンシー | `git merge upstream`。義務ではない |
| 読者に対する損害 | 人 | **ライセンシー**（発信者） | 越境の断り書きは読者保護。ソフトはそれを消させない |
| テナント間の分離 | コード（予定） | ライセンシー | 今はストア共有・単一トークン（未決事項 11）。**テナントを置く前に直す** |

**要点。** ライセンサーが引き受けるのは「ガードレールをコードとして置くこと」までで、その結果は引き受けない。
ライセンシーが引き受けるのは「設定に書いたルールが正しいこと」と「公開されたもの全部」。
この線をひな型の全部で一貫させる。

## 5. 契約の形

### 契約A — 先行利用許諾（来週から）

正式リリース前に少数（技術者から、のち非技術者）に使ってもらい、壊れ方を報告してもらうための許諾。
参照体系の「無償・労務なし・フィードバックが対価」をそのまま使う。加えるのは3つ。

- **初日から実投稿を許す**が、[先行利用者の最初の一週間](../2-setup/first-week.md) の3条件を契約上の前提にする。前提を外れて起きたことは、利用者の判断
- **未公開版であること。** コードと文書は第三者に見せない。ただし自分の SNS に投稿された文章は当然公開される
- **終わり方。** いつでもやめられる。やめたら `.amp/` はそのまま手元に残り、コードは削除。正式版に移るときは契約Bに置き換える

テナントは置けない（契約Bの追加条項が要る）。料金はゼロ。
ひな型: [`contracts/early-access-licence.md`](../../contracts/early-access-licence.md)。

### 契約B — マスターライセンス契約（正式）

2階への配布契約。参照体系の「⓪ 直接ライセンス」と「② 非独占的販売代理」を、このソフト向けに1つにした。

- **許す:** リリースリポジトリのフォーク、自社アカウントでの運用、`platform.config.yaml`・`prompts/`・`.env.local` の自由な編集、**自分のインスタンスのための `src/` の改変**（役割の追加を含む）
- **許さない:** 再配布、改変版の頒布、第三者へのサブライセンス（テナント条項を付けたときを除く）、コードのガードレールを外して「プラットフォームが検査している」と称すること
- **対価:** 当面は無償。フィードバックが対価（5.4節の決定）。ライセンシーの収益とテナントへの課金はライセンシーのもの
- **更新:** ライセンサーが出したものは使える。出す義務はない
- **サポート:** 無い。文書と `doctor` が全部
- **終わり方:** 30日前通知。支配権変更で自動終了。終了後コードは削除、データは手元に残る
- **テナント条項（任意）:** 契約Cを使ってテナントを置く権利。3階の規約は2階が自分で整える。2階は1階より広い権利を3階に渡せない

ひな型: [`contracts/master-licence.template.md`](../../contracts/master-licence.template.md)。

### 契約C — テナント利用規約

既存の下書き（チェックリスト形式）を `contracts/tenant-terms.template.md` に移し、今回の実装に合わせて3点足した。
非アクティブ化と停止がテナントの投稿に何をするか、データのエクスポート（素の JSON）、AI 生成物の権利帰属は「帰属する限りにおいて」。

### 契約D — アカウントの譲渡（今は決めない）

育ったアカウントを売る場面。決めるべきことは提案 §6.3 に書いた。
契約上いま言えるのは1つだけで、それを B に入れた: **ライセンスは買い手に付いていかない。** 買い手は B を自分で結ぶ。渡せるのはデータ（`.amp/` のそのアカウント分と設定ブロック）で、SNS アカウント自体の譲渡は各 SNS の規約が制限しうる。ここは法務。

### 5.4 対価の選択肢

| 形 | 向く場面 | 実装 | 注意 |
|---|---|---|---|
| **無償＋フィードバック** | 先行利用。参照体系の基本形 | フィードバックは `.amp/setup.json`（未実装）と報告 | ライセンサーが個人で、能動的な報酬を受け取れない事情があるならこれ一択 |
| **定額（インスタンス／アカウント単位）** | 正式版の基本形 | `licensing.model: subscription` は3階向け。2階向けは契約書の数字 | 消費税・インボイス、通貨 |
| **確定報酬の一定割合** | 成果連動を望むとき | `amp statement` の算術 | **監査権が要る**（数字はライセンシーの手元にしか無い）。虚偽申告を契約で担保する必要。複雑 |
| **持分** | ライセンサーとライセンシーが同一グループ | 契約外 | 参照体系の想定。一般のライセンシーには使えない |

**決定（2026-09-02）: 当面は先行利用も正式版も無償＋フィードバック。** ライセンシーには自分の事業として頑張ってもらい、
その収益はライセンシーのもの。ライセンサーは請求経路にも取り分にも入らない。
定額・成果連動は将来の選択肢として残す。切り替えるときは契約Bの第4条を差し替え、消費税・インボイス・監査条項をそのとき整える。

### 5.5 対価の選択肢を、お金の流れで言い直す

「ライセンシーが月にいくら、何に対して、誰に払うか」で読むと4つはこうなる。

| 形 | ライセンシーが払うもの | ライセンサーが確かめる手段 | 向き・不向き |
|---|---|---|---|
| **無償＋フィードバック** | お金は払わない。壊れ方の報告を送る | 報告が来ているか | 先行利用に向く。正式版で採ると収入はゼロ。**個人が金銭を受け取らない形にしたいなら、これしかない** |
| **定額** | 月ごと（または年ごと）に決まった額。成果が出ていなくても払う。単位は「運用アカウント1件」か「インスタンス1台」 | アカウント数を数えるだけ | いちばん単純で揉めにくい。請求書・消費税・インボイスが要る。稼げていないライセンシーには重い |
| **成果連動** | ASP が**確定**した報酬の一定割合。通貨ごと | ライセンシーの手元の数字を信じるか、監査する権利を書くか | ライセンシーには売りやすい。ライセンサーには**確かめる手段が乏しい**。報酬の確定は ASP の締めに依存し、月ごとに変わる。通貨も混ざる |
| **定額＋成果連動** | 低い定額に、上限つきの割合を足す | 両方 | 折衷。条文は長くなる |

**当面は無償なので、3階建てのままでよい。** 将来、個人がライセンサーのまま有償にするなら、体系は4階になりうる。
個人（1階）→ 商業の窓口となる法人（2階、販売代理契約）→ ライセンシー（3階、マスターライセンス）→ テナント（4階）。
お金はライセンシーから法人へ流れ、個人には流れない。参照体系の「①／② 販売代理契約」はこの2階のための契約で、
その場合はこの文書の「契約B」を法人が結ぶ側に置き直す。有償化を考える時点で、この前提を採るかを先に決める。

### 5.6 読者が海外、ライセンシーが海外

2つは別のことなので、分けて扱う。

- **読者市場が米国**（日本のライセンシーが米国の読者に出す、または米国の商材を日本の読者に出す）。
  契約の準拠法には関係しない。関係するのは `markets:` の中身と、契約第3条の「読者の国の規制はライセンシーが守る」。
  FTC の指針を `markets[us]` に正しく書くのはライセンシーの仕事で、例の値は出発点にすぎない。これは既に契約に書いてある。
- **ライセンシーが米国法人**。ここで初めて、英語の契約文、米国州法の準拠法、米国側の法務が要る。
  日本語正本のまま「参考訳」を付ける手もあるが、米国法人に日本法・日本語の契約を結ばせるのは現実的でない。
  **ライセンシーごとに準拠法を選べる構造にする**（日本のライセンシーは日本法・日本語、米国のライセンシーは米国某州法・英語）。
  ひな型は日本語を先に確定させ、英語版はその翻訳ではなく米国側の法務が起草し直す。

### 5.7 個人のまま続けられるか

いま個人で、これからもずっと個人事業のままでいられるか。**法律上はいられる。**
ソフトの著作権は個人が持てるし、ライセンスを許諾する行為に許認可は要らない。
実務上の違いは1つだけで、屋号は契約の当事者にならないので、署名欄は個人名と住所になる。
法人格が要る場面は無く、法人化はいつでも「そのほうが得か、安全か」の判断でしかない。

判断が変わる引き金は4つ。どれも今は当たっていない。

| 引き金 | 何が起きるか | いつ効き始めるか |
|---|---|---|
| **無限責任** | 個人事業は事業の債務と個人の財産が分かれない。免責と責任上限が第一線で、それが破られたときの壁が個人には無い | テナントを置くとき、有償にするとき、ライセンシーが増えたとき。中間手段として IT 賠償責任保険（E&O）がある |
| **税** | 個人の所得は累進（住民税込みで最大約55%）。法人の実効税率はこれより低い | 継続的な利益が出てから。目安として課税所得800万〜1,000万円あたりと言われるが、数字は税理士に確認する。**無償の間は論点にならない** |
| **相手の都合** | 法人のライセンシーは、購買規程・与信・反社チェックで個人との契約を通しにくいことがある。米国法人なら W-8BEN、TIN、源泉徴収と日米租税条約の届出が個人の手元に来る | 最初の法人ライセンシー、最初の海外ライセンシー |
| **承継** | 個人だと本ソフトの著作権は相続財産になり、事業の継続が本人に依存する。ライセンシーは「更新は続くのか」を気にする | ライセンシーが本業でこれに依存し始めたとき |

**いまの立場: 個人のまま。** 無償で、テナントもおらず、相手は先行利用者だけなので、4つのどれも差し迫っていない。
法人化は「有償にするとき」「テナントを許すとき」「法人ライセンシーが個人との契約を断ったとき」のいずれかが来た時点で、そのときの数字で決める。
5.5節の4階建ては、その判断の一つの形（法人を窓口に置く）にすぎない。

**契約の側では、いま1行だけ用意しておく。** 将来法人化したとき、既存のライセンシー全員から同意を取り直さずに契約を移せるように、
甲が自ら支配する法人へこの契約上の地位と本ソフトの権利を承継させられる、と書いておく。乙の側の譲渡禁止はそのまま。
契約A第7条と契約B第9条に入れた。実際に移すときは、個人から法人への著作権の譲渡契約と税務の手当てが別途要る。

## 6. 決めてもらうこと

| # | 事項 | 選択肢 | 決まらないと |
|---|---|---|---|
| 1 | **ライセンサーの主体** | **決定: 個人。将来も個人事業のまま続けられる（5.7節）** | 署名欄は個人名と住所。法人化は有償化・テナント・法人ライセンシーのいずれかが来たときに判断する。契約には「甲が支配する法人への承継」を先に入れてある |
| 2 | **準拠法と言語** | **決定: 日本法・日本語を正本**。ただし読者市場には米国も入る | 読者が米国にいることと、ライセンシーが米国法人であることは別の話（5.6節）。日本のライセンシーには日本語版。米国法人がライセンシーになる時点で英語版と米国側の法務が要る |
| 3 | 正式版の対価 | **決定: 当面は無償。対価はフィードバック。** ライセンシーは自分の事業として運用し、その収益はライセンシーのもの。テナントへの課金もライセンシーの事業（`licensing:`）で、ライセンサーは取り分を持たない | 有償に切り替えるときは契約Bの改定（5.4節の選択肢から）。個人が金銭を受け取る形にするかはその時点で 7節の法務確認 |
| 4 | 独占か非独占か | 非独占（推奨） | 参照体系は独占版もある。誰かに市場を任せるなら独占 |
| 5 | `src/` の改変を許すか | 許す（推奨。`extending.md` と整合）／設定とプロンプトのみ | 禁止すると「7つ目の役割を足せる」が嘘になる |
| 6 | テナントを既定で許すか | 追加条項で許す（推奨） | 未決事項 11（承認者の識別）が先。分離が無いのに許すと3階の約束が守れない |
| 7 | 先行利用の秘密保持 | あり（推奨）／なし | 無いとリリース前のコードが出回る |
| 8 | ライセンサーが受け取るフィードバックの範囲 | 手動の報告のみ／`.amp/setup.json` などのファイル／集計データ | 個人情報が混ざる経路（読者のリファラ、国）を決めておく |
| 9 | 責任上限の数字 | 3階: 直近3か月の利用料（参照体系）／2階: 支払済み料金の総額／無償なら0 | 無償契約の上限0は法務の確認事項 |
| 10 | 既定の禁止カテゴリ | 医療・金融・ギャンブル・アダルト・MLM・債務…から選ぶ | `markets[].restrictedCategories` の既定値と契約の文言を一致させる |

## 7. 法務に必ず聞くこと

ここは私が判断してはいけない。ひな型はいずれも仮置き。

- **ステマ規制・景表法の責任主体。** 規制の名宛人は「事業者（広告主）」で、アフィリエイターの位置づけは ASP 契約と運用実態で変わる。ライセンシーが広告主側とみなされる場面はあるか
- **AI 生成物の権利帰属。** 日本法では AI が生成した文章に著作権が認められない可能性がある。契約の「投稿はライセンシーに帰属する」は「帰属する限りにおいて」としか書けない
- **無償契約での免責・責任上限の有効性**（消費者契約法はテナントが事業者なら外れるが、個人事業主は微妙）
- **読者のデータ。** リダイレクトが記録するのはリファラと国コードまで。IP は保存しない。これが個人情報に当たるか、プライバシーポリシーが要るか
- **越境。** 米国の商材を日本の読者に出す構成で、米国側の規制（FTC）が読者保護として及ばないという整理は正しいか
- **アカウント譲渡と SNS 規約**（契約D）
- **税。** 定額の消費税・インボイス、越境ライセンスの源泉、成果連動の計算根拠
- **個人ライセンサーの対価。** 個人が直接ライセンス料を受け取ることに、居住国・在留資格・税務上の制約があるか。あるなら 5.5節の4階建て（法人を窓口にする）が前提になり、契約の当事者が変わる
- **個人のまま続けることの限界**（5.7節）。無限責任をどこまで契約と保険で埋められるか、法人化を考えるべき利益規模（税理士）、契約A第7条・契約B第9条の「甲が支配する法人への承継」条項がライセンシーの同意なしに有効か
- **米国法人のライセンシー。** 準拠法・言語をライセンシーごとに選ぶ構造で問題ないか。英語版は日本語版の翻訳ではなく米国側で起草するか

## 8. 実装との対応 — 契約が参照できるもの

契約の条項は、ソフトが実際に残す記録を指せる。逆に、記録が無いことは約束しない。

| 契約が言うこと | ソフトの記録・機能 |
|---|---|
| 承認は人がした／`auto` を選んだ | `decisions`（`decidedBy` / `autoResolved`）、監査ログ |
| 開示は検査された | 検品レポート（`inspections`）の findings。承認画面の PR 表記の表示 |
| いつでも止められる | `amp pause`。有効な設定も鍵も要らない |
| やめてもデータは手元に残る | `.amp/` は素の JSON。ライセンサーは受け取らない |
| 設定はライセンシーの管理下 | `platform.config.yaml` は git 管理外。追記は控え付き（`config-backups/`） |
| 料金の算術 | `amp statement`（請求書ではない、税は載せない） |
| 何が配られたか | `RELEASE.json` の sha256 |
