## 1. 着想

Threads運用代行会社の構成を、そのままエージェントの組織にする。

- **リサーチ担当** — 毎朝、伸びてる投稿を集めて再現性のあるバズの型だけを抜き出す
- **企画担当** — これまでの伸びデータと照らして「次に出す投稿ネタ」を10本提案する
- **ライティング担当** — 1行目でスクロールを止めるフックから本文まで設計して1投稿仕上げる
- **検品担当** — 別のAIが「AIっぽい言い回し」を見つけて人間味のある一人称に直す
- **分析担当** — 投稿ごとの伸びを見て、勝ちパターンだけを毎日アップデートする
- **投稿担当** — いちばん伸びる時間に予約投稿して、コメントの下書きまで用意しておく

**人間の仕事は、提案に「OK」と言うことと、どの投稿から出すかを最後に決めることだけ。**

この一文が製品の制約そのものである。人間の作業がこの2つを超えたら、それは設計の失敗として扱う。

これは1日の話である。アカウントの**中**の仮説（何を書くか、どの型が効くか）は機械が作って検証する。
アカウントを**増やす**判断は人間のものだが、その候補は機械が根拠付きで出す。週に1回、
**探索担当**が全アカウントの数字を読み、次に試すアカウントを提案し、人が採否を決める（5.9）。
会社としての思想（`company.principles`）と、どのアカウントでもやらないこと（`company.boundaries`）を
1か所に書き、全役割が全アカウントでそれを読む。アカウントが20になっても1つの会社である理由はこれ。

## 2. これは何で、何ではないか

**プラットフォームである。** ライセンシーが公開リリースリポジトリの複製を自分のアカウントに持ち、設定1ファイルを書いて運用する。ニッチ・文体・チャネル・市場・案件のどれもコードに入れない。変更に `src/` の編集が要るなら、それは `platform.config.yaml` のスキーマの欠陥であって、機能ではない。

**端末を前提にした製品ではない**（2026-09-11 決定。3.1）。ライセンシーはボタンで自分のアカウントに配置し、以後ブラウザだけで運用する。`git clone` も `npm` も要求しない。CLI（`amp`）は開発者と、端末を持つ運用者のための第二の入口であって、ライセンシーの前提ではない。**この一文に反する要件は、書かれた時期にかかわらず古い。**

**運用者1人向けの運用ツールではない。** ただし最初のライセンシーは1人運用者である想定で、複数人での同時編集は要件に含めない。

**投稿代行サービスではない。** アカウントの資格情報は運用者自身のもので、契約は運用者とASP・チャネルの間にある。

## 3. 利用者

体験を設計する対象。**4種類いて、それぞれ見る画面が違う。**

| # | 誰 | 何をする | どこで触るか | 頻度 |
|---|---|---|---|---|
| 1 | **運用者** | 提案にOKを出す。投稿順を決める | 承認画面 / CLI | 1日2回、各30秒 |
| 2 | **ライセンシー** | 配置し、初期設定し、**更新を受け取る** | 承認画面 / GitHub の画面 / 設定ファイル | 導入時、および更新のたび |
| 3 | **テナント** | ライセンシーの環境で自分のアカウントを運用する（3階層目・任意） | 運用者と同じ画面 | 1日2回 |
| 4 | **読者** | 投稿を読む。リンクを踏む | SNS上の投稿とコメント | — |

**1が主役。** 1の体験が30秒で終わらないなら、他が何点でも失敗である。

3は契約上の階層であって、同時に画面を触る複数人のことではない。承認画面は今のところ
トークン1つで、誰が承認したかを区別しない（未決事項 11）。テナントを実際に置くなら、
それより先に承認者の識別が要る。

4を忘れないこと。読者は「AIが書いた投稿」を読まされる側で、開示・断り書き・海外案件の注意はこの人のためにある。

### 3.1 それぞれ何ができる人か

**行動ではなく能力で書く。** 「何をするか」は設計を縛らないが、「何ができるか」は縛る。
上の表には長いあいだこの節が無く、**その空白がこの製品でいちばん高くついた欠陥だった**（末尾に経緯）。

| 能力 | 運用者 | ライセンシー | テナント | 読者 |
|---|---|---|---|---|
| 端末（シェル） | **前提にしない** | **前提にしない** | 前提にしない | — |
| `git clone` / `merge` / `push` | しない | **しない。** GitHub の画面でファイルを作る・ボタンを押す・PRを読んで統合するまで | しない | — |
| YAML の読み書き | しない | **する。** ただしブラウザのエディタ上で | しない | — |
| 障害時の自己診断 | 承認画面 | **承認画面。** `doctor` は端末が要るので、診断手段として数えない | 承認画面 | — |
| 秘密の値を作る | — | **する。** ただし `openssl` ではなく、自分で決めるかパスワード管理アプリで | — | — |

**2026-09-11 決定: ライセンシーは端末を持たない。** パートナーは開発会社ではなく運用会社であり、
そもそも Cloudflare を選んだ理由が運用負担を無くすことだった。ここを「持つ」に戻すなら、
配置・診断・更新の3つが同時に変わる。

この決定から直ちに従うこと:

- **`doctor` は診断手段ではない。** 6節「壊れたことが人に届くこと」と8節の接点3が負うのは承認画面である
- **`amp init` も打てない。** 初期設定ウィザードは「作るか」ではなく**前提条件**である（2026-09-11 決定、旧未決事項 7）。
  無ければライセンシーの初日は、ブラウザで428行のYAMLを手書きすることから始まる。

  **形も同時に決まっている**（設計は[オンボーディング](../2-setup/onboarding.md)）。Worker のファイルシステムは
  読み取り専用なので、ウィザードは設定ファイルを保存しない。**できあがった YAML を表示し、
  ライセンシーがコピーして自分のリポジトリに貼る。** 貼れば push になり、自動で再デプロイされる。

  **承認画面が `platform.config.yaml` を書き換える設計にはしない** — これは制約への妥協ではなく、
  上の「YAMLの読み書きはする」と同じ思想の側にある。理由は2つ: 428行の大半を占めるコメントが設定の説明
  そのもので、オブジェクトを書き戻すとそれが消えること。そして「自分の設定は何か」の答えが2箇所になると、
  フォークして中を読む人にとっての監査の前提が崩れること。**生成器であって、常駐エディタではない。**

  **実装済**（v0.4.0）。7問に答えると設定ファイルができあがる。

  **この判断をやり直す条件:** 設定の変更頻度が「初回＋まれ」ではなくなったとき。日常的に画面から
  変える運用が要るなら、真実を1箇所に保ったまま画面から変える方法（例えば画面が差分をコミットする）を
  先に設計する必要がある。いまそれを作らないのは、その頻度が実在するかが分かっていないからである
- **フォークの同期（`Sync fork`）が使えない。** 更新に仕組みが要る（未決事項 17）
- **契約Bの文言が実態と違う。** `contracts/master-licence.template.md` 2.1(a) は「リリースリポジトリを
  フォークし」と書くが、ボタンが作るのはフォークではなく複製である。**法務確認の対象**（未決事項 5）。
  技術の固有名に依存しない書き方（「複製を作成し、方法を問わない」）を提案するが、勝手には直さない

**そして規則を1つ。**

> **配布方法・実行環境を変える判断は、必ずこの表に戻る。表を書き換えていないなら、その変更は終わっていない。**

実際に起きたこと: フォーク前提から Deploy ボタン前提への移行は「オンボーディングの改善」として行われ、
この表に戻らなかった。**ボタンは便利機能ではなく、ライセンシーが誰かを変える判断だった。**
その間、要件は存在しない人物を記述し続け、そこから出た欠陥が4つある — 端末前提の合言葉生成、
端末前提の更新経路、端末前提のデプロイキー設置、そして打てない `doctor` を診断手段に据えたこと。
最後のものは設計注釈（`docs/_drafts/design/canvas.json`）に**気づきとして書かれていたのに、
要件に戻らなかった**。気づいた場所に留まった観察は、要件を嘘のままにする。

## 4. 中核となる運用モデル

### 1日の流れ

```
analyze → research → plan → 【OK？】 → write → inspect → schedule → 【順番は？】 → publish
```

括弧が人間の止まる場所。他は止まらない。

| 時刻 | 起きること | 人間 |
|---|---|---|
| ローカル 06:30（設定可） | 分析担当が昨日の数字と報酬を読み、プレイブックを再採点 | — |
| | リサーチ担当が伸びた投稿を集め、再現性のある型を抽出 | — |
| | 企画担当がその日の案を提案 | — |
| **承認①** | **企画の承認** | **約30秒** |
| | ライティング担当が承認された案を執筆 | — |
| | 検品担当が書き直し、出してはいけないものを止める | — |
| | 投稿担当が枠を決め、コメントを下書き | — |
| **承認②** | **投稿の承認と順番決め** | **約30秒** |
| 各枠 | 投稿とコメントが出る | — |
| 翌 06:30 | 数値の取得、成果の取り込み（次のサイクルの最初に分析担当が行う。常時ではない） | — |

### 自律度は3段階

| 値 | 挙動 | 使いどころ |
|---|---|---|
| `manual` | ①②の両方で停止。何も事前選択しない | 導入直後。何を却下するかを学ぶ期間 |
| `assisted`（既定） | ①②の両方で停止。推奨を事前選択済み。OKは1クリック | **設計の基準となる運用形態** |
| `auto` | ①②を機械が解決。枠の前なら `amp pause` で止められる（投稿1件だけの取り消しは未実装。未決事項 8） | プレイブックに実績が溜まってから |

`auto` への移行は時間の問題ではなく**コンプライアンス上の露出の判断**である。コードのガードレールは効き続けるが、誰も読まずに公開される。

### 答えないことも答えである

その日の案を全部却下できる。サイクルは正常終了し、何も書かれない。これはエラーではなく情報で、週に3回起きたら企画のプロンプトかプレイブックに問題がある。

承認に人間が来なくても壊れない。状態は永続化され、承認済みの投稿は出続け、翌日のサイクルは予定どおり始まる。

**そして、答えないまま日が変わったら、その日の判断は期限切れになる**（2026-09-11 決定）。
アカウントのタイムゾーンで日付が変わった時点で、残っていた判断は `expired` になり、そのサイクルは
`cancelled` で終わる。判断そのものも、そこに載っていた案も消さない — 監査ログと記録には残り、
「この日は誰も答えなかった」が後から読める。

**なぜ捨てるのか。** 3つある。

- **一斉公開になる。** 過ぎた日の承認を今押すと、枠は過ぎた日の時刻で決まり、配信は
  「枠が来たもの」を出すので、**その日の全部が間隔ゼロで同時に出る**。`minMinutes` が
  その日に限って効かない。運用として事故であり、画面の注意書きでは止まらない
- **企画が古い。** 案は前日の数字とその日のリサーチから作られている。1日ずれた提案は、
  ずれた根拠に基づいている
- **溜まること自体が信号である。** この製品の約束は「1日2回・各30秒」で、溜まった判断は
  その前提が崩れているサイン。溜めた分を後から一括で流すより、落として今日から立て直すほうが、
  運用として正しい

**画面には出る。** 期限切れになったことは「最近の動き」に残り、何日分が落ちたかが読める。
黙って消えるのは、溜まっていたことに気づけないという同じ問題を作る。

**この判断をやり直す条件:** 承認を「その日のうち」に限らない運用が要るとき — 例えば週末を挟む
運用や、承認者が複数の時間帯にいる場合。そのときは「期限を設定にする」（`console.gateExpiresAfterDays`）
が素直な形で、いまそれを作らないのは、必要かどうかが分かっていないからである。

### 止められる

3つ目の操作。理由を言葉にできる前に押せること。

- `amp pause` は、有効な設定・生きたAPIキー・動くアダプタのどれも要らない。設定が壊れていれば生の
  ファイルからデータの置き場所だけ読む。止めに行く理由になりうるものが、止められない理由になってはいけない
- 失敗は閉じる側に倒れる。停止ファイルが読めなければ「停止中」として扱う
- 捨てない、遅らせる。停止中に枠が過ぎた投稿は `resume` 後に出る
- できないこと1つ: チャネル自身の予約に渡った投稿の取り消し。その一覧を出して、チャネル側で消してもらう
- 効くのはサイクル・承認・配信の**入口**。`auto` でチャネルに渡している最中の1件は渡り切る

## 5. 機能要件

### 5.1 6つの役割

各役割は **型付きの入力を受け、1つの仕事をし、型付きの出力を返す**。次に何が動くかを決めない。他の役割を知らない。人間の存在を知らない。

| 役割 | 入力 | 出力 | 要件 |
|---|---|---|---|
| 分析 | 期間 | 分析レポート | 数値と成果を取り込み、実績を「それを主張した型」に紐付けて再採点する。**サイクルの最初に走る**（今日の企画が昨日の証拠から作られるため） |
| リサーチ | 期間 | 参考投稿 + 型候補 | **再現性のある「形」だけ**を抽出する。話題は抽出しない。存在しない投稿IDを引用した型は幻覚として捨てる |
| 企画 | 件数 | 案 N 件（既定10） | 各案に「根拠（どの型・どの過去投稿の数字か）」と「失敗の仕方」が必須。実在しない型・案件の参照は落とす |
| ライティング | 承認済みの案1件 | 完成した投稿1件 | リンクは執筆前に発行し、実URLを渡す（本文に置くかは文章の流れに任せる。プレースホルダは禁止）。チャネルの形式（短文／スレッド／長文）に従う |
| 検品 | 下書き1件 | 検品レポート + 書き直し | **別の呼び出し**であること。機械的検査 → モデルの書き直し → **同じ機械的検査をもう一度**。決めるのは2回目。AIっぽさは「モデルが自分の書き直しに付けた点」と「機械判定が同じ書き直しに付けた点」の悪いほう |
| 投稿 | 検品を通った下書き | 予約投稿 + コメント下書き | 枠は実測データから選ぶ。リンクは本文にあってもなくても**1コメント目に必ず置く**（開示つき） |

**7つ目の役割を足せること。** 法務レビュー、翻訳、サムネイル設計。1ファイル書いて1ステップ足すだけで済む構造にする。

### 5.2 サイクル

- **1運用アカウント・1ローカル日につき1サイクル。** IDは日付から導出し、生成しない（2回叩いても2日目が始まらない）
- **各ステップ後に永続化する。** 承認は何時間も待ちうるので、途中でプロセスが死んでも失うのは1ステップ分まで
- **失敗したステップから再開する。** 1日をやり直さない
- 1案の執筆が失敗しても、他の案の1日を巻き添えにしない
- **再開で副作用を繰り返さない。** チャネルが受理した投稿を再送しない、書けた下書きを書き直さない。
  現状はステップ単位の永続化で、ステップの途中で落ちた場合はこれを保証していない（未決事項 13）

### 5.3 承認（HITL）

- 提示は**選ぶ・並べる**の2操作だけ。編集させない
- 部分的な並び順を受け付ける。指定されなかったものは提案順で後ろに続く
- 不明なID・重複IDは黙って落とす。朝7時にリストを触る人間はそうするから
- 上限を超える選択は**拒否し、上限を明示する**
- 一度解決した判断は二度解決できない
- **選ばれなかった投稿は取り消す。** 翌日に漏れ出させない

### 5.4 プレイブック（学習）

これがあるから運用が複製ではなく複利になる。

- 証拠は**新しさで重み付け**する。先四半期に効いた型は、今効く型ではない
- 十分な証拠が溜まるまで確信度を「わからない（0.5）」側に縮める。**3回うまくいっただけでは証明ではない**
- **昇格より引退に多くの証拠を要求する。** 誤って昇格＝凡庸な投稿1本、誤って引退＝効くものを捨てる
- 企画には常に**未検証の型の枠を確保**する。これがないと最初に当たった型に収束して学習が止まる。
  ただし1日2本以下の運用では確保しない。1枠しかないのに探索に使うのは博打であって探索ではない。
  実績のある型が足りないときだけ、未検証の型で埋める
- 引退した型は企画に出さない。それが引退の意味である

### 5.5 チャネル

必要なのは4つだけ。**何が効いているか探す**（リサーチ）、**選んだ時刻に出す**（投稿）、**結果を読み戻す**（分析）、**最初のコメントを置く**（リンク投下）。

- チャネルは形式を宣言する: `short` / `thread` / `longform`。280字の投稿とnoteの記事は「同じ文章の長短」ではなく別の仕事なので、ライティング担当に伝える
- ネイティブ予約がないチャネルは、デーモンが枠まで保持して出す
- チャネル1つが落ちても、そのチャネル分の入力が減るだけで1日は止まらない（リサーチと分析について。
  投稿については下の制約を見よ）
- 汎用HTTP（webhook）で繋げること。多くの運用者は既にMake/Zapier/n8nを持っている
- **現状の制約:** 1運用アカウントの投稿先は `channels` の先頭1つ。残りはリサーチと数値の取得にだけ使われる。
  同じ投稿を複数チャネルに出す、チャネルごとに書き分ける、はどちらも未実装（未決事項 10）

### 5.6 アフィリエイト

**リンクを貼ることは要件の中心ではない。** 中心は「計測経路のどこが切れているか」を毎日測れることである。

```
止まる → 読む → 信じる → 押す → 買う → 承認される
```

- 投稿 → リンク → クリック → 成果 → **型** まで紐が繋がっていること。「一番シェアされた投稿が一番稼いでいない」が見えることが価値
- リンクコードは **(運用アカウント, 案件, 投稿) から決定的に導出**する。再起動やデータ再構築で、既に稼いだ成果が孤児にならないため
- 成果はASPの成果IDで重複排除する。同じレポートを2回入れても壊れない
- **紐付かなかった成果は握り潰さず「未帰属」として数える。** 監査ログと分析レポートに件数が残る
  （`amp report` への表示は未）。その数が増えるのは症状である
- **計測経路が閉じているかを、最初の投稿の前に検査できること。** 投稿 → 反応 → リンク → 成果 → 報酬の
  どこが戻ってこないかを `doctor` が言う。切れたまま回した期間は測り直せない
- 報酬は**通貨別**に扱う。為替レートを持たない（誰も記録していないレートで間違った数字を出すより、2行のほうがましだから）

### 5.7 市場とクロスボーダー

**規制は広告主ではなく読者に従う。** 米国の商材を日本の読者に紹介するなら、適用されるのは景表法とステマ規制で、開示は日本語で書く。商材側の国が決めるのは、読者がクリック前に知るべきこと（通貨・配送・言語サポート・誰と契約するのか）だけ。

起動時に拒否すること:

- 運用アカウントの市場が案件の `targetMarkets` にない → **起動しない**（テリトリー外運用で数ヶ月後に成果を全否認される事故を止める）
- クロスボーダーなのに読者への断り書きがない
- その市場が全面禁止しているカテゴリの組み合わせ

公開時に強制すること:

- 開示文は**読者の市場のもの・その言語**
- 禁止表現は「プラットフォーム共通 ∪ 読者の市場」
- クロスボーダーの断り書きは、**モデルに聞くのではなく文字列の有無で検証**する。書き直しで消えたら付け直し、それでもなければ止める

### 5.8 ライセンス階層

```
[3階] テナント／エンドユーザー
   ▲  マルチテナント利用規約（サインアップ時に同意）
[2階] ライセンシー（運営会社）
   ▲  マスター販売代理契約（フォークを許諾する契約）
[1階] ライセンサー（著作権者）
```

- 2階への配布は**公開リリースリポジトリの複製**。開発リポジトリの中身は渡らない。
  複製の作られ方はライセンシーの能力で決まり（3.1）、端末を持たない既定の経路では
  Deploy ボタンが複製する — **フォークではない**ので、フォーク由来の仕組み（`Sync fork`）は当てにできない
- 3階の課金は `none` / `subscription` / `revshare` の設定切り替え。**「サブスクかレベシェアか」を作る前に決めなくてよい**こと自体が要件
- 出すのは計算過程（statement）であって請求書ではない。税は扱わない
- 正式リリース前は、2階の契約の代わりに**先行利用許諾**（無償、フィードバックが対価、実投稿は3条件つき）
- **当面、2階からライセンサーへの金銭対価は無い。** ライセンシーは自分の事業として運用し、収益もテナントへの課金も自分のもの。ライセンサーは取り分を持たない
- 育ったアカウントを売るとき、ライセンスは買い手に付いていかない。買い手は自分で結ぶ
- 契約体系・責任分担・未決の論点は [契約体系と責任分担](licensing.md)。ひな型は `contracts/`。**すべて法務の確認前**
- 決定の履歴（契約・置き場所・オンボード）は [決めたことと、その理由](../5-project-management/decisions.md)

### 5.9 探索（アカウントを増やす判断の支度）

設計は [探索](../3-development/exploration-design.md)。

- **探索担当は日課に入らない。** 週1回（`company.exploration.everyDays`）か、`amp scout` で人が呼ぶ。
  毎日の2つの判断に3つ目を混ぜない
- **読むのは集計まで。** 各アカウントの投稿数・中央値・クリック・成果・通貨別報酬・実績のある型の名前・案件カテゴリ。
  個々の投稿や下書きは渡さない。1アカウントの学習が別アカウントに漏れない
- **提案には、仮説・根拠・リスク・最初の3本・やめる条件が必須。** やめる条件のない提案は落とす
- **コードで落とす:** 設定に無い市場、その市場で禁止のカテゴリ、既存アカウントと同じニッチ、
  その市場で許されていない案件の参照。落とした理由は監査ログに残る
- **採用は設定ファイルへの追記。** `ventures[]` のブロックをコメント付き・`active: false` で `ventures:` の直下に文字列として差し込む。
  他の行には触らず、控えを `.amp/config-backups/` に残し、通らない追記はしない。人が文体を直し、`active: true` にして再起動する
- **全アカウント一覧**（`amp portfolio`・承認画面）が、探索担当の読む数字と同じものを人にも見せる。
  合計は件数と通貨別まで。通貨をまたいで足さない
- **アカウントは削除せず非アクティブにできる。** 管理画面のボタン1つ、または `amp venture deactivate`。
  設定ファイルは触らず、再起動も要らず、学んだこと・履歴・成果は残り、再開は1クリック。停止とは別物（停止は緊急・全体・閉じる側、非アクティブは判断・個別・開く側）
- **見直し候補は数字からコードが付ける。** 判断できる本数があって反応がリンクに届いていない、または中央値が会社の半分未満。
  印は提案で、切るのは人

## 6. 非機能要件

**監査可能性。** 「なぜこの投稿が提案されたか」を後から人間が辿れること。各提案は根拠とリスクを持ち、各公開投稿は下書き・案・型・その型が依拠した証拠まで遡れる。メモリ上にしか存在しない成果物はこの約束を壊す。

**再開可能性。** どの瞬間にプロセスを落としても、次のコマンドで続きから走る。

**設定だけで運用できること。** ニッチ・文体・チャネル・閾値・市場・案件の変更に `src/` の編集を要さない。役割の着眼点を変えるのは `prompts/` の編集で行い、コードのフォークを要さない。

**依存の少なさ。** ライセンシーは自分の手元にあるものを監査する。複製であってもコードは全部そこにあり、それが監査可能性の実体である。実行時依存は `@anthropic-ai/sdk` の1つだけ。増やすには、ライセンシーが納得する理由が要る。

**トランスパイル不要。** `npm install` して `node src/cli.ts` で動く。Node が型をそのまま剥がすので、コンパイル成果物は無い。
ただし**Cloudflare 経路には束ね工程がある** — `npm run build`（`scripts/bundle-worker.ts`）が設定とプロンプトを Worker に埋め込む。
Worker にはファイルシステムが無いため、これは省けない。「ビルド不要」と一語で書くと、この2つが混ざる。

**費用ゼロで一周できること。** APIキー・チャネルトークン・ASP契約のどれもない状態で、全工程が模擬アダプタで走る。「試せます、ただし先にこの3つを用意してください」は試せるとは言わない。

**状態が読めること。** 運用データは素のJSON。何かおかしいときに `cat .amp/cycles.json` が正当なデバッグ手段であること。

**壊れたことが人に届くこと。** 投稿の失敗、チャネル認証の失効、計測経路の切断は、運用者が見る場所に出る。
**その場所は承認画面である** — `doctor` は端末を要し、ライセンシーはそれを持たない（3.1）。
現状、停止と計測経路はそこに出るが、投稿失敗と認証失効は監査ログにしか残らず、押して知らせる手段がない（未決事項 9）。

**直っていることが人に届くこと。** プラットフォームの修正が出ていること、それが自分の運用に何を意味するかが、
ライセンシーの見る場所に出る。**更新があるのを知らない人は、知っていて手間がかかる人より危険である** — 前者は直っている不具合を踏み続け、
気づく契機が無い。この要件は経路に依存しない: 自分の版を知り、公開リリースリポジトリを読むだけで満たせ、git も権限も要らない。
**実装済**（v0.3.0、2026-09-11）。承認画面の最上部に静かな1行が出る。複製が自分の版を `RELEASE.json` で持ち、
公開リリースリポジトリが公開している版と突き合わせるだけなので、認証も git も要らない。
届かないとき・未リリースの複製では、誤りではなく**何も出ない**。
受け取る側の仕組みとは別の要件であり、先に満たすべきはこちらだった。当てる側は未決事項 17 に残る。

**設定は起動時に読む。** デーモンは `platform.config.yaml` を起動時に1回読む。変えたら再起動。
これは制約であって、ホットリロードは要件にしない（未決事項 12 で再考）。

## 7. ガードレール（コードで守るもの、プロンプトに置かないもの）

モデルに「これはコンプラ的にOK?」と聞けばOKと答える。開示文字列の有無を機械的に検査する側は言いくるめられない。**以下はコードに置き、検品の書き直しの前と後の両方で走らせる。決めるのは後の実行。**

- 案件を含む投稿の開示（読者の市場の文言・言語で）
- 禁止表現（プラットフォーム共通 ∪ 市場）
- クロスボーダーの断り書きの存在
- チャネルの文字数
- AIっぽさのヒューリスティック（**モデルが自分の書き直しに付けた点と、機械判定が同じ書き直しに付けた点の悪いほう**を採用する。
  兄弟の仕事を採点するモデルも、自分の仕事を採点するモデルも、利害関係者ではない）
- 1日の投稿上限（運用アカウント単位）、投稿間隔の下限

この一覧を外せる設定は `blockOnComplianceFindings: false` の1つだけで、開示・禁止表現・断り書きのブロックをまとめて
警告に落とす。詰まった投稿を出すためのスイッチではなく、その市場で不要と確認できたときのもの。設定リファレンスにそう書く。

そこで置いた仮説は3つ:

- 10案を平等に並べない。推奨3件だけを開いてチェック済みにし、残りは畳む。
- 枠の時刻は人間に触らせない。決めるのは「どれを、どの枠に」だけ。
- 詳細画面にも編集を置かない。編集を許した瞬間、人間の仕事は2つでなくなる。

| 15 | **ライセンシーはどこで動かすか** | 調査は [どこで動かすか](../4-operations/hosting.md)。サーバレス（Cloudflare Workers $5/月 か Vercel Pro $20/月）にするなら、保存先をファイルから SQL に移す（ポート1本）ことと、ライセンシーの固定費を前提にすることを同時に決めることになる。Docker で各社に置くなら実装は不要だが、ドメインと TLS がライセンシーに残る。**既定は1つに決める必要がある** — 手順書とオンボードが分岐すると機能しない |
| 16 | ~~**承認画面を俯瞰と個別に分けるか**~~ **決定・実装済**（2026-09-09。3階層に分けた） | いまは1本のスクロールで全部が「全アカウント」の視点。アカウントの中に入る場所がないので、失敗の理由も操作もアカウント一覧の行へ押し込まれる（実際に表が壊れた）。比べる画面と、1つを直す画面は目的が違う。提案は [承認画面の分け方](../3-development/console-architecture.md) |
| 17 | **ライセンシーはどう更新を受け取るか** | **気づく**側は6節「直っていることが人に届くこと」に格上げ済み — 経路に依存せず満たせるので、判断を待つ理由がない。**当てる**側に判断が残る: ボタンが作るのは複製で、フォークでもワークフローの届く先でもないため、GitHubの純正機能では閉じない。案と本当の費用、私たちが全ライセンシーのリポジトリに書き込み権限を持つ案を**却下した理由**、判断をやり直す条件は [更新を受け取る](../3-development/taking-updates.md)。**この件と、配布・リリース経路に触れる前に必ず読む** |

## 11. 意図的にやらないこと

- **為替換算。** 通貨をまたいで足さない
- **請求・決済・税務。** 明細（計算過程）までで止める
- **運用者による下書き編集。** 直したくなったら却下する。編集させ始めると「2つの仕事」の約束が壊れる
- **複数人での同時運用。** 単一運用者前提。データディレクトリはプロセスロックで守る（承認画面の2つのタブは守らない。未決事項 11 と同根）
- **設定のホットリロード。** 変えたら再起動
- **1日3つ目の承認。** 追加には相応の理由が要る
- **APIを持たないASPごとの個別実装。** CSVレポートで受ける
