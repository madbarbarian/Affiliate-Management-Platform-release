# 決めたことと、その理由

決定の記録。**何を決めたか、なぜか、どこに書いてあるか、何がまだ決まっていないか。**
新しい決定は下に足す。覆したときは消さずに「覆した」と書く — なぜ一度そう決めたかは、
次に同じ問いが来たときに効く。

設計そのものは各設計文書に、要件は
[要件定義](../1-requirements/requirements.md)にある。ここはその索引ではなく、
**判断の履歴**である。

## 2026-09 契約

### ライセンサーは個人。将来も個人事業のままでよい

法人格が要る場面は無い。屋号は契約の当事者にならないので署名欄は個人名と住所になる、
という実務上の違いだけ。法人化を考える引き金は4つ（無限責任・税・相手の購買規程・承継）で、
無償でテナントもいない現状はどれも当たらない。

**いま打った手は1つだけ。** 甲が自ら支配する法人へ契約上の地位を承継できる条項を、
契約A第7条と契約B第9条に入れた。これが無いと、法人化したときに
既存のライセンシー全員と結び直しになる。

→ [licensing.md 5.7](../1-requirements/licensing.md)、`contracts/`

### 準拠法は日本法・日本語。読者市場が海外であることとは別

読者が米国にいることは `markets:` の中身の問題で、契約の準拠法とは関係しない。
米国法人がライセンシーになる時点で初めて、英語版と米国側の法務が要る。
ひな型は日本語を先に確定させ、英語版は翻訳ではなく向こうで起草し直す。

### 当面は無償。対価はフィードバック

ライセンシーは自分の事業として運用し、その収益も、テナントに課金するならその料金も
ライセンシーのもの。ライセンサーは請求経路にも取り分にも入らない。
定額・成果連動の文案は契約B第4条の末尾に残してあり、切り替えるときは
消費税・インボイス・監査条項をそのとき整える。

**未決:** 無償契約での免責・責任上限の有効性は法務確認。ひな型は仮置き。

## 2026-09 どこで動かすか

### 既定は Cloudflare Workers。Docker の経路は残す

Vercel と比べた: 無料枠が**商用禁止**（アフィリエイトは確実に該当）、Hobby の Cron は
1日1回が上限で投稿の枠に届かない、Pro は $20/月。Cloudflare は無料枠に非商用条項が無く、
Cron は毎分、**課金が CPU 時間なので待ち時間が数えられない** — 1サイクルの大半は
モデルの応答待ちなので、いちばん高くつくはずの部分がタダになる。$5/月。

無料プランは 10ms CPU で足りない（設定を読んでスコアを計算するだけで超える）ので、
現実解は Workers Paid。

**Worker は入口を1つ増やすだけで、置き換えではない。** `daemon` はそのまま動く。
`workerd` は Node ではないので CLI は手元に残る必要があり、実行環境は2つになる。

→ [hosting.md](../4-operations/hosting.md)、[cloudflare-design.md](../3-development/cloudflare-design.md)

### 保存先は SQL。3テーブル、1行1 JSON

型ごとの列を作った瞬間に、型を変えるたび移行が要る（未決事項 14）。
1行1 JSON なら、いまのファイル版と同じく型の変更に移行が要らない。
`find(predicate)` は JavaScript の述語なので SQL に翻訳する道が無く、
ファイル版と同じく全件読んでメモリで絞る — **挙動が変わらないことが唯一の約束**。

`seq` は並び順のためだけにある。upsert は書き換えないので、差し替えても末尾に動かない。

**判明したこと:** `node:sqlite` が Node に内蔵されている。D1 は SQLite なので、
**本番で D1 が実行するのと同じ文をテストで本物の SQLite に対して走らせられる。**
依存は増えない。設計時に想定していた「フェイクドライバ」は不要になった。

### 停止と非アクティブはポートの向こうへ。安全性の判断はポートの外

`StateStore` の `read` は**同期のまま**。tick は公開する前にこれを見るので、
`await` を挟むと停止を見落とす窓ができる。DB 版は `refresh()` が読んだ
スナップショットから答え、**最初の成功した refresh までは全部 `unreadable`** —
つまり停止扱い。refresh を忘れた入口は止まる側に倒れる。

「読めないときどうするか」は保存先の都合ではなく安全性の本体なので、
`pause.ts`（fail-closed）と `venture-state.ts`（fail-open）に残した。

### `--dry-run` は「何が動いているか」の答えを持たない

一度これを間違えた。`--dry-run` に空の状態ストアを渡したせいで、実機が停止中でも
`doctor --dry-run` は「動いている」と答えた。**確認したいから dry run を打つのに、
実機と違うことを言うのは無意味以下。** 保存先・モデル・アダプタは差し替える。
停止と非アクティブは差し替えない。

→ 実バイナリを起動するスモークテストで固定（`test/cli.smoke.test.ts`）

**未決:** `cycleStartsAt` の「分」が Workers で無視されること（重いサイクルを
1時間 Cron に置いて CPU 15分枠を取るため）を受け入れるか。

## 2026-09 ライセンシーの最初の1時間

### 受け取るのはリンク1つ。clone も YAML も出てこない

Deploy to Cloudflare ボタンが、リポジトリの複製・D1 と Durable Object の作成・
秘密の入力・ビルド・配置・CI/CD をやる。こちらが用意するのは
`wrangler.jsonc`、`.env.example`、`package.json` の説明文、README の1行。

### ドメインは要らない

`workers.dev` のアドレスが無料で公開されるので、`/go/` が初日から動き、
**計測経路が初日に閉じる**。旧ステップ9（ドメインの用意、30分〜、脱落率が最も高い）が
丸ごと消えた。Cloudflare 自身は workers.dev を事業の中核には勧めていないので、
案内は「始めるには十分、育ったら独自ドメインへ」。

### デプロイ画面でモデルの鍵を必須にしない

必須にすると「**鍵を1つも持たずに製品が動くところまで行ける**」という設計の核が、
いちばん最初の画面で壊れる。**合言葉は必須** — 同じアドレスで承認画面が開くため、
そこは後回しにできない。

**2026-09-08 に本当になった。** それまでは半分嘘だった — 出荷している例の設定が
`llm.provider: anthropic` だったので、鍵を入れるまで承認画面が開かなかった。
実デプロイの1画面目で発覚。例を `mock` に変え、鍵は手順4で入れるものにした。

見つからなかった理由が本題で、**スモークテストが例の設定を `mock` に書き換えてから
試していた**。「壊れた例の設定は誰かの初日ではなくここで落ちる」ためのテストが、
落ちようのない形に直してから走っていた。書き換えを外すと12件中10件が赤になる。
README はこの問題を知っていて、直さずに回避策（`--dry-run` を足せ）を書いていた —
端末があれば回避できるが、Cloudflare には端末が無い。

### 設定は承認画面が保存しない。ライセンシーが貼る

Workers のファイルシステムが読み取り専用だから、ではない。**設定はライセンシーのもので、
変更の履歴は本人の控えに残るべき**だから。探索担当の提案を採用したときも同じ経路を通る。

→ [onboarding.md](../2-setup/onboarding.md)、`docs/_proposed/design/onboarding/`

### 壊れていても、リンクと死活だけは答える

`/go/<code>` は、設定が検証に落ちても、合言葉が無くても答える。公開済みの投稿に
入っているリンクは取り消せないし、**記録されなかったクリックは後から数えられない**。
そのためにリダイレクトは `Store` と id と時計しか要求しない（`RedirectDeps`）。
`/healthz` はデータベースより手前。

### Cron の重複はロックで止める。実装は Durable Object

Cron は前回の実行中に発火しうるし、再試行もされる。ロックが無ければ同じ投稿が
2回出る。Durable Object は名前ごとに1つしか存在せず、1度に1リクエストしか扱わない
ので、**それ自体がロック**である。ロックは保持者を記録する — TTL を超えた保持者が
遅れて release したときに、その後に取った人のロックを外さないため。

### ライセンシーのフォークでは、設定を commit する

こちらのリポジトリでは `platform.config.yaml` は git-ignore のまま（実アカウントが
入るため）。**ライセンシーのフォークでは ignore しない。** Cloudflare ではビルドが
設定を Worker に埋め込むので、commit されていない設定は**デプロイが一度も見ない設定**で、
例のまま立ち上がる。リリーススクリプトが `.gitignore` を書き換え、理由もそこに書く。

設定に秘密は入らない（環境変数の名前だけ）という規則があるので、commit しても安全。
これが成り立たなくなったら、この判断も崩れる。

### 検証はアカウント無しでほぼ済んだ（2026-09-04）

`wrangler dev --local` が本物の `workerd` とローカル D1 を立てるので、
「デプロイしないと分からない」と書いた2つはアカウント無しで潰れた。
バンドルは通り（790 KiB）、SDK を含むモジュールグラフは起動し、**1日ぶんの流れが
丸ごと `workerd` の上を通った**（企画10案 → 承認 → 執筆 → 検品 → 枠決め）。

残るのは、本番の鍵が要る Anthropic への実呼び出しと、
ホストされた側（`workers.dev` のアドレス、Cron の実発火、Deploy ボタン）。

### 実デプロイで残り3つのうち2つが片付いた（2026-09-08）

`amp.madbarbarian.workers.dev`。**両方の Cron が自力で発火し**、1日ぶんが
ホストされた側を通った — 毎時Cronが企画からゲートまで、承認のあと執筆・検品・枠決め、
毎分Cronが枠の来た1件だけを公開。ティックが何度走っても公開イベントは1件のまま。

**`/go/` のクリックが1件記録された。** 「ドメインは要らない」は、これで実機の裏付けが
ある。旧ステップ9を消した根拠がここで確定した。

**3番目の画面でいきなり止まった。** 例の設定が `llm.provider: anthropic` で、
鍵が無いと承認画面が開かなかった。スモークテストが例を書き換えてから試していたので
誰も気づいていなかった。→ 別項

残るのは実ストリーミング呼び出しと Deploy ボタンの経路。

## 2026-09 検証を誰がやるか

### 参照環境は自分で持つ。$5 は検証費用ではなく設備

ライセンサーは運用者ではないので、「先行利用者（知人）に動かしてもらいながら
直せばいい」という選択肢があった。**採らない。** 順番を決めたのは費用ではなく、
2つの検証が別のものを試しているという点。

**インフラの不具合はフィードバックではない。** 残っている workers.dev の
アドレス・Cron の実発火・実ストリーミング呼び出しは、動くか動かないかの話で、
相手に見つけさせる種類のものではない。一方**オンボーディングが分かるかどうかは、
書いた本人には試せない** — 初見の目は一度しか使えず、それをバグの発見に
使うのは高すぎる。

**相手の側では目が見えない。** Cloudflare には端末が無いので `doctor` が無く、
相手のアカウントの `wrangler tail` も見られない。動いているものを一度も
見ないまま、動かないものを直すことになる。

順番はどのみち強制されてもいる。ボタンには公開リリースリポジトリとリリース発行が
要り、まだどちらも無い。自分のデプロイはいますぐできる。

無料プランで代用しない。CPU 10ms で落ちたときそれがコードのバグに見えるので、
**曖昧な結果は無い結果より悪い。**

$5/月は1回の検証費ではなく、ライセンサーである限り要る**参照環境**の維持費と
考える。「壊れた」と言われたときに突き合わせる先が無い状態には戻らない。

→ [deploy-checklist.md](../4-operations/deploy-checklist.md)

### 自分の D1 の id は、リリースに乗るファイルに書かない

`wrangler.jsonc` はライセンシーにそのまま届く。id をそこに書くと**全員が
こちらのデータベースを指す設定を受け取る**（開けはしないが、設定としては誤り）。

最初の手順書は「placeholder に戻してから release を切る」と書いていた。
**戻し忘れる手順は、いつか忘れる。** `npm run deploy` が `.env.local` の
`AMP_D1_DATABASE_ID` を見て一時ファイルを作るようにして、戻す手順自体を消した。
変数が無い経路 — つまりライセンシー — は以前と1文字も変わらない。

id は秘密ではないが `.env` ではなく `.env.local` に置く。`.env` は commit される。

## 2026-09 オンボード

### 初期設定は生成器にする。設定ファイルを画面が持ち続けることはしない

ライセンシーの初日は428行の YAML を開くところから始まっていた。
[オンボード設計](../2-setup/onboarding.md)がそこを最大の脱落点と名指ししている。
6問に答えると設定ファイルができあがる形にした（v0.3.0 以降）。

**テキストを埋める。オブジェクトを書き戻さない。** 428行の大半はコメントで、
なぜその値なのかを説明している。パースして書き戻すとそれが消える。
これは承認画面を設定の編集器にしない理由と同じもので、要件3.1に決定として記録した。

### ライセンシーのリポジトリへの書き込みは、いまも「しない」

**貼り付け1回は残す。** 2026-09-12 判断。

中身を URL に載せる案は実測で否定した。GitHub の新規ファイル画面はクエリで本文も
受け取れるが、GET の上限が約2KB、この設定ファイルは URL エンコードで41KB
（日本語がパーセントエンコードで1文字9文字になる）。**ファイル名だけは載る**ので、
「Add file → Create new file → ファイル名を打つ」の3手順は消した。

自動でコミットするには資格情報が要り、形は2つしかない。

| 案 | 状態 |
|---|---|
| 私たちがホストする GitHub App | **却下**（[更新を受け取る](../3-development/taking-updates.md) 4節）。理由はいまも有効 |
| ライセンシーが発行したトークンを自分の Cloudflare に置く | **見送り。** 2つのダッシュボードにまたがる約15手順で、途中で権限スコープを選ぶ必要がある。トークンを知らない人には貼り付け1回より難しい |
| **GitHub Device Flow** | **将来の選択肢。** 下記 |

### 「読むのは画面、変えるのはファイル」は、いまのところ妥協である

**2026-09-12、オーナーからのフィードバック:**「結局、編集はファイルで、になってるんだね。いまいちだよね。」

**そのとおりである。** 上の2つの理由（コメントが消える／真実が2箇所になる）は本物だが、
**理由があることと、使いやすいことは別**である。ライセンシーから見れば
「設定画面があるのに、設定できない」で、それは変な製品である。ここを
「設計上正しいので問題なし」と記録すると、次に読む人が問題を問題として見なくなる。

いまの形は「読む」と「変える」を別の場所に置いた結果で、一貫はしているが親切ではない。
**今回はこれで試すと決めた**（オーナー判断、2026-09-12）。試した結果が、次の判断の材料になる。

**本当に解くなら、画面から変えて、その変更が git のコミットになる形である。**
真実は1箇所のまま、履歴も残る。ただしそれには「ライセンシーのリポジトリに書ける権限」が要るので、
**この課題と下の Device Flow は、実は同じ1つの課題である。** 別々に解こうとしないこと。

### 将来: GitHub Device Flow（未着手）

`github.com/login/device` にコードを入れて承認するだけで、ワーカーがライセンシーの
リポジトリに設定ファイルをコミットできるようになる。貼り付けが消える。

**却下した App 案とは別物である。** 発行されるトークンはライセンシー本人のもので、
1人分だけ、本人がいつでも剥がせる。私たちは何も保持しない
（Device Flow はクライアントシークレットを使わない）。
要件6節「ライセンシーが自分の手元にあるものを監査する」は保たれる。

**いま作らない理由:** ライセンシーがまだ1人もいない。貼り付け1回が本当に脱落点なのかは、
誰かが実際につまずいて初めて分かる。確かめていない問題に工数を使わない。

**着手する条件:** (1) ライセンシーが実際にここで詰まった、または
(2) 最初の1人に見せる体験として、貼り付けを残したくないという営業判断。

## 2026-09 最初のライセンシーに渡す前に

### 鍵ゼロで試せる範囲を、先に人に試してもらう

> **2026-09-16 改めた。** 模擬モードでは「出てくる案が読むに値するか」に答えが出ないと分かり、
> 最初のテストは**本物のモデル**で行うことにした。→ [最初のテストで確かめること](#最初のテストは本物のモデルで投稿はしない)。
> 下の「本物のSNSはその結果を見てから」は変わらない。

**2026-09-12 決定。** 最初のテスト利用者（オーナーの配偶者）には、
**模擬モードで最初の1時間と最初の3日**を試してもらう。本物のSNSとASPは、その結果を見てから。

理由は2つ。

- **`threads.ts` は一度も動いたことがない。** 実装はあるが、HTTPの経路をテストが
  一度も通っていない（[外とつながる部分](../3-development/integrations.md)）。
  動いたことのないコードで実アカウントに投稿すると、失敗したときに
  「製品が悪いのか設定が悪いのか」が切り分けられない。**最初の1人の信頼は一度しか無い**
- **ASPの審査に数日かかる。** どのみち今日は始められない

**そして、鍵ゼロで確かめられることが、まだ一度も人に試されていない。**
貼り付けが本当に脱落点なのか、出てくる案が読むに値するのか、毎日の承認が30秒で
終わるのか。[オンボード設計](../2-setup/onboarding.md)が「鍵を1つも持たずに
製品が動くところまで行けること」を第一原則に置いたのは、まさにこれを確かめるためである。

### Cloudflare では国内ASPの成果を取り込めない（未解決）

`csv` アダプタは `node:fs` を読む。**Workers にファイルシステムは無い。**
要件3.1は「ライセンシーは端末を持たない」と決めている。この2つが重なると、
**Cloudflare のライセンシーは A8.net の成果を1件も取り込めない。**

既定の置き場所を Cloudflare に寄せる判断（未決事項15）をしたとき、
**この帰結が検討されていなかった。** 要件3.1の規則
「配布方法・実行環境を変える判断は、必ずこの表に戻る」が、また同じ形で効いている。

案は3つ（画面からCSVをアップロード／ASPのAPI／メール転送）。
比較は[外とつながる部分](../3-development/integrations.md) 4節。**まだ決めていない。**

### Amazon アソシエイトは、構造ではなく規約の問題

ポートは Amazon を受け入れられる（`buildTrackedUrl` がアソシエイトタグの穴）。
**問題は運営規約がリダイレクトによる隠蔽を禁じていること**で、このプラットフォームは
全てのリンクを `/go/<code>` に通す設計である。

「Amazon だけ直リンクにする」は技術的には簡単だが、**「計測はこちらが持つ」という
設計の一部を Amazon に対してだけ降ろす**ことを意味する。**法務判断であり、
勝手には決めない。** 未決事項として扱う。

## 2026-09 Amazon アソシエイトを調べた

### Amazon は初日に使えない。「読者がいる人」向けの制度である

オーナーが「Amazonアフィリエイトってどうやるの、やったことがない」と訊いたので調べた。
**A8.net と同じ順番で扱えないことが分かった。**

登録しただけでは審査が始まらない。**180日以内に、自分のリンク経由で他人が3件買う**ことが
審査の受験資格になる。自己購入は数えず、家族・友人に頼むのは規約違反である。

**これは製品の順番の話になる。** 最初のライセンシーに「アフィリエイトを登録してください」
と言うとき、A8.net（審査に通れば読者0人でも案件を持てる）と Amazon（読者がいないと
180日で失効する）は**同じ日にできる作業ではない**。オンボードで並べて見せると、
Amazon 側が必ず失効する。

順番は **A8.net で案件を持つ → 読者ができる → Amazon を足す**。

### 日米どちらもやるなら、Amazon 側の条件は2倍になる

ライセンシーが日本と米国の両方を視野に入れていると分かった。

**プラットフォーム側は既に答えが出ている。** [越境の設計](../7-references/cross-border.md)が
「市場が2つならアカウントを2つ」「コンプライアンスは読者に従う」「`targetMarkets` の外は
設定時エラー」「通貨は足さない」を決めており、設定ファイルにも `us_main` の雛型が
コメントで入っている。**ここは追記であって、コード変更ではない。**

増えるのは Amazon 側である。Amazon.co.jp と Amazon.com は別プログラムで、登録も審査も
タグも支払いも別。**3件の壁が2回ある。** 読者が日本に偏っていれば米国側は埋まらない。

OneLink（各国のアカウントを紐づけて、読者を自国のストアへ送る仕組み）はあるが、
**紐づける先には先に通っている必要がある** — 審査を省く道具ではない。

**推奨は「最初のテストは日本1市場から」。** 3件の壁を2回同時に越えるのは、
いちばん難しいところを倍にして注意を半分にする動きである。米国側は後から
`ventures:` への追記で足せる。

### 確かめていないことを、確かめたと書かない

Amazon 公式の `affiliate.amazon.co.jp` は、開発環境のネットワーク制限で直接読めなかった。
上記のうち**紹介料率の細目・OneLink の挙動・対象SNSの一覧は二次情報**である。

とくに**対象SNSに Threads が見当たらない**件（未決事項19）は、事実なら既定のチャネルと
Amazon が両立しないという重い話になる。それを二次情報のまま設計に反映するのは、
この3日間に3度やった失敗（既にある記録を読まずに動く）の裏返しの失敗になる。

**登録画面を5分開けば確定する。** 確定するまで設計は変えない。

### 採らない理由は2つ。どちらも技術ではない

1. **契約の形が違う。** Max / Pro は**契約者本人が、提供元の画面を通して対話的に使う**
   ための契約で、第三者の自動サービスの裏側として動かすのは利用条件の外である。
   そしてこれは**ライセンス製品**なので、土台が利用条件違反だと、
   **その違反ごとライセンシーに相続させる**ことになる。

2. 🔴 **動く場所が合わない。これが決定的。**
   この製品の核は**誰もいない時間に Cron が起きてサイクルを回す**ことで、
   一方サブスクは**ログインした人間のセッション**に結びついている。
   Worker が持てる「Max の資格情報」は存在しない。
   **「人がいなくても動く」という製品の定義そのものと噛み合わない。**

### ただし、問いの中に本物の変種がある

**人がいる前提なら成立する。** 運用者はどのみち1日1回、承認画面を開く。
`src/llm/` は差し替え口になっていて（いま `anthropic` と `mock`）、3つ目を足せる。

**失うもの:** 自律性（「寝ている間に会社が動く」が消える）と、
**要件3.1**（ライセンシーは端末を持たない）。Claude Code を動かす機械と契約が要る。

**つまり別の製品である。**悪い案という意味ではなく、**売っているものが変わる。**

### economics は、思ったより小さい

| | |
|---|---|
| Cloudflare | **$5/月**（必須。サブスク経路にしても消えない） |
| AIモデル | 実測で**毎日 $0.3〜0.6**（月 $9〜18） |

9/16 の $4.2 の跳ねは、**2026-09-20 に直した毎時やり直しのバグ**が原因だった。
上限（`company.retry.maxCycleAttempts`）を入れたので、同じ跳ね方はしない。

**削れるのは月 $10 前後**で、そのために自律性と要件3.1を捨てる取引になる。

### 開発者側では試す（2026-09-20 オーナー）

**ライセンシー向けには採らないが、開発者はどのみち画面の前にいる**ので、
切り替えを試す価値はある。**いまのテスター確認が終わってから。**

🔴 **着手するなら要件3.1の能力表の書き換えから始める。**
`CLAUDE.md` が「配り方・動く場所を変えるなら、要件の能力表を書き直すまでが変更」と
決めている。表を直さずに作ると、**存在しない人間を説明した要件が残る**
（この repo は一度それで欠陥を4件出している）。

## 2026-09-21 ライセンシーは「初日に1回、以後は何もしない」にする

**オーナーの目標:**「ライセンシーは、基本的にほぼ何もしないで進められるようにしたい」

### 覆った前提

`taking-updates.md` の案B（2026-09-11 採用）は「置いたワークフロー自身も以後の更新に
含まれるので、**1回置けば古くならない**」を根拠にしていた。**誤りだった。**

同期が運ぶのは直下の `update-workflow.yml` だけで、**実際に動いている
`.github/workflows/take-updates.yml` には届かない。**v0.8.1 でそれを踏み、
`amp-test` で手で貼り替えた。**案Bの費用は「初日に1手順」ではなく
「初日に1手順 ＋ 更新器が変わるたびに1手順」だった。**

### 決定: 案D（更新器を「薄い殻」にする）を採る（オーナー）

殻は `scripts/` のスクリプトを呼ぶだけの数行にし、中身は同期で新しくなる場所に置く。
**App も、トークンも要らない**ので、`taking-updates.md` 4節で却下した理由には触れない。

**初日の1回は消せない。**Deploy ボタンがワークフローを運べないのは Cloudflare 側の制約で、
こちらのリポジトリをどう直しても越えられない。

### 🔴 順番の制約: 案Dより先に、テスターに渡さない

手順書（4-2）・オンボードの板（`Ready.dc.html`）・その README は、どれも
「更新を受け取る口を**1回だけ**作る」と書いている。**初日の設置は本当に1回なので、
案Dが入っていれば正しい。**案Dより先に渡すと、この3か所は**黙って嘘になる**
（更新器が変わるたびに、書いていない貼り替えが要る）。

### 案E（インストーラ型）は別に判断する

**オーナーの問い:**「インストールするときに『いいですか？』と出てシステム領域にも
コピーする。それと同じでは？」

**形は同じ。**ただし Deploy ボタンの「いいですか？」は **Cloudflare のもの**で、
何の権限を求めるかは Cloudflare が決める。`workflows` を求めていないので、
OK を押しても `.github/workflows/` に書く許可は含まれない。**他社の確認画面に
1行足すことはできない。**

**この問いで新しい道が見えた。** 4節で却下したのは**恒久的に**書ける状態で、
インストーラ型は**1回使って捨てる**ので別物である。代償は「私たちがサービスを
動かし続ける」こと — この製品がこれまで避けてきた性質。**案Dの上に乗せられるので、
案Dを先に入れ、案Eはあとで判断する。**

### 実測で分かったこと

- **貼り替えは、マージから5分**（`amp-test`・2026-09-21）。「ブラウザで2分」は楽観的だった。
  読む時間を含めると5分。**コピー元と1バイトも違わず貼れていた**
- **`.github/` の変更でも、Cloudflare は配置し直す**（main への push なら中身に関係なく）。
  ただし `.github/` は Worker に入らないので、作り直された Worker は前と同じ。
  **害のない、空振りの配置**である

## 2026-09-21 案D は本物で動いた。そして殻には、予告された変更が1つある

v0.9.0 を出し、`amp-test` で本物の移行を通した。古い更新器で取り込み → マージ →
殻を貼る（マージから2分、コピー元と1バイトも違わず）→ **殻で Run workflow が success**
（上流を取り、差分が無いので何もせず終了）。**殻とスクリプトが本物の runner で動いた最初の1回。**

### 案D の第1版の仕様は、危険だった（記録として残す）

最初に書いた仕様は「走っているスクリプトを rsync が上書きする罠があるので、`/tmp` にコピーして
実行せよ」だった。レビューで2つとも誤りと分かった。

- **罠は起きない。**rsync は一時ファイルに書いて rename するので、実行中のプロセスは古いファイルを
  読み続けて完走する（再現で確認）
- 🔴 **そして対策が本物の事故を作るところだった。**スクリプトが自分の位置から根を求めると、
  `/tmp` では根が `/` になり、**`rsync --delete` が別の場所を消す**

**起きない罠を防ごうとして、実害のある削除を仕込むところだった。**言語を node にし、根は
`$GITHUB_WORKSPACE` から取り、rsync の前に3段で止める形にした（上流の取り置き先とリポジトリが
重なったら止まる — 根が `/` ならこれで止まる）。

### 殻に置いてはいけないもの

**殻は1文字変えると全員に貼り替えを頼む**ので、sha256 をテストで固定した（関所）。
出す前に、**古くなる事実を3つ抜いた**：除外の一覧（**既に `.git` が抜けていた**）・約束の一覧
（**既に `TAKE_UPDATES_SCRIPT` が抜けていた**）・「1分後に PR ができる」（実際は6.4分待った）。
**直せない側に、直す必要が出る事実を置いていた。**原則: **古くなりうる事実は殻に書かない。**

### 予告された変更

- **`actions/checkout@v4` は Node 20 向けで廃止予定。**いずれ `@v5` にする。**殻の変更なので
  全員に貼り替えを頼む。**そのときは CHANGELOG に理由を書き、sha256 の関所を意図して越える
- **`ubuntu-latest` は 2026-10-19 から Ubuntu 26。**殻は変わらない。runner の node が
  `engines` の 22.18 以上かを、その前に確かめる

## 2026-09-23 トップ画面から判断待ちを外す（複数アカウント前提へ）

### 決めたこと

**トップ画面は「どのアカウントが、どんな状態か」だけにする。**判断待ちの中身、
予約中の投稿、手渡しの投稿カードは**各チャンネルの画面へ移す**（実は既に在る —
`#/ventures/<id>` は最初からそのアカウントの判断待ちだけを出していた。
トップが重複して出していただけである）。

トップに残るもの：アカウントごとの状態、直近の数字（全アカウント合計）、最近の動き、
探索の提案（アカウントに属さないため）。

**1アカウントのための分岐は作らない。**1つでも複数でも同じ手順にする。

### なぜ覆したか

[コンソールの設計](../3-development/console-architecture.md) §3 は3階層を決め、
第1階層について「判断待ち、予約中の投稿。**変えない。ここが今も正しい**」と書いていた。
**これを覆す。**

- **前提が変わった。**あの記述は「毎日30秒で終わる」を守るためのもので、**1アカウントなら正しい。**
  オーナーは 2026-09-23 に「**複数アカウント前提です**」と決めた。3アカウントで実際に運用した上での判断
- **複数になると、いまの設計は逆に働く。**3アカウントぶんの判断が1本のリストに混ざる。
  オーナーの言葉：「全体的に、セクションもなく、わかりにくい」
- **手順を2つ持つと、片方が腐る。**1アカウント用と複数用を分けると、手順書・設計キャンバス・
  画面の説明がすべて2本になる。**このリポジトリは「同じ問いに2つの文書が答えていて、
  生きているのは片方」を繰り返し踏んでいる**（2026-09-20 の「現在地」4箇所など）。
  オーナーの判断：「いずれ複数アカウントになるという考えから、同じ操作手順にしたらいい」

### 条件（同時に満たすこと。どれも欠けると引き算が危険になる）

1. 🔴 **コメントアウトではなく消す。**残せば腐り、理由を知らない誰かが戻す。
   消して、戻したくなったときのためにこの記録を残す
2. 🔴 **バッジが構造物になるので、検査を付ける。**いまは判断待ちそのものがトップに出ているので
   見落としようがない。外すと**「対応が要る」と伝えるのはバッジだけ**になり、
   バッジが 0 を出せば仕事は静かに止まる。**トップのバッジの数が、実際に待っている判断の数と
   一致することを検査するテスト**を必ず付ける。
   このリポジトリには同じ形の記録がある —
   「**記録が無いことと、何も起きていないことは、画面の上で見分けがつかない**」
3. **`console-architecture.md` の「変えない」を、理由ごと書き換える。**
   UX 提案書（`console-ux-proposal.md`）の節の順番と、設計キャンバスの板
   （`Main.dc.html`・`Idle.dc.html`）も揃うまでが完了

### バッジは2種類にする（時間に縛られているものだけ強くする）

**手渡しの投稿カードだけは性質が違う。**判断待ちは「あなたが決めるまで待つ」もので、
1時間遅れても失うものは少ない。**手渡しは、枠の時刻にあなたが投稿しないと枠が過ぎる。**
機械が特定の分に人を待っている、唯一のもの。

案は3つあった：(1) 手渡しだけトップに残す、(2) 全部外してバッジを2種類にする、(3) バッジ1種類。
**(2) を採る**（2026-09-23 オーナー合意）。理由は、(1) は「トップは状態だけ」という
原則に例外を1つ作ることになり、**例外は増える**から。

バッジは少なくとも3つの事実を区別する必要がある：
**承認が要る** ／ **いま投稿する番です**（強く） ／ **失敗している**。
3つ目は `console-architecture.md` が既に「失敗だけは例外にする」として決めている —
一覧に出さないと気づくのが翌週になる、という実績がある。

### これは何を無駄にしないか

**門を「推奨」と「そのほか」に割った変更（PR #72）は、そのまま生きる。**
`renderDecision` はトップとチャンネル画面で共有されており、分割はどちらでも効く。
